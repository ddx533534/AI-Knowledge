# 03-Daily — AI 日报

## 用途

本目录收两类内容：

1. **每日简报**：每天定时生成的 AI 行业简报 + 单个 GitHub 仓库深度分析。面向的读者画像固定为：**具备跨端渲染与 AI 工作流编排经验、正在转向 AI 方向**。
2. **专题**：对某篇外部材料（厂商博客、论文、框架文档）的**全文中文翻译**与配套的**总结分析**，一份材料对应两篇文档。日报是每天固定的产出，专题是遇到值得逐字读的材料时才开，两者不混写。

与知识库其它目录的关系：

- 本目录是**简报与转述产出**，不进入 `01-Knowledge`（要闻属二手转述），也不属于 `02-Work-Practice` 的实践记录。
- 简报中"待核实问题"若被持续跟进并形成独立技术结论，再按 `AGENTS.md` 的整理约定提炼到 `01-Knowledge`。
- 简报内容**不自动**成为知识节点：要闻属二手转述，不满足"可复查技术证据"的准入要求。

## 文件约定

| 文件 | 说明 |
| --- | --- |
| `YYYY-MM-DD.md` | 日报正文，`git diff` 友好，便于检索。站点页面由 `site/build.mjs` 从这里生成，不再单独手写 HTML |
| `YYYY-MM-DD-<主题>.md` | 专题正文。同一天既有日报又有专题时靠主题名区分；一份专题的译文与分析各占一个文件，文件名前缀相同、后缀不同 |
| `assets/YYYY-MM-DD/` | 当日插图。SVG 为自绘，位图取自源文档；都按 `figN-<短名>.<ext>` 命名，N 与正文的「图 N」一致 |
| `assets/YYYY-MM-DD-<主题>/` | 专题插图。一份专题里两篇文档共用这个目录，第二篇的图加前缀区分，如 `analysis-figN-<短名>.svg`，N 按那一篇自己正文的先后连排 |

## 内容结构

### 日报

1. **今日要闻（5 条）**：每条含 标签 / 结论 / 事实 / 对你（读者）的相关性 / 来源与日期。
2. **今日精选仓库（1 个）**：基本信息表 → 解决什么问题 → 核心机制 → 可借鉴的设计决策 → 与既有经验映射 → 上手路径 → 风险 → 待核实问题。
3. **今天可以动手的三件事**。
4. **来源清单**。

### 专题

拆成两份文档，各管一件事：

1. **译文**：完整翻译，不改原文的论证顺序。开头写清原文标题与作者、发布日期、原文链接、译文与核实日期，以及「哪些图是自绘、哪些取自原文」。
   - 小节层级、代码块、脚注、外链、图注全部对应原文，不增删论点。
   - 译者自己加的话必须显式标「译注」，不要混进正文。
2. **分析**：开头直接回答「这份材料真正改掉/立起的是哪一条」。后续章节只放证据、动作与边界，不把开头的判断再讲一遍。

| 分析要覆盖的 | 写法 |
| --- | --- |
| 推翻了什么 | 逐条对照「常见说法 / 原文的反驳 / 反驳的判据」 |
| 立起了什么 | 逐维度对照表，维度要能对齐 |
| 证明不了什么 | 单卡、单模型、单次实验这类限制写进表里，不写成普适结论 |
| 口径核对 | 厂商自测、原文正文、自己从公开数据算出的数字对不上时，三个都写，标清来源与统计区间 |
| 落地情况 | 材料发表到现在，相关实现有没有进产品；官方文档怎么写的，写日期 |
| 代价 | 性能 / 功能 / 硬件与适用范围分三类，逐条给来源 |

### 补充核实

同日后续产生的新问题（读者追问、需要回源码验证的疑点）以「二·补 / 补充核实」小节追加到当日文件，不新建文件、不覆盖原有结论。补充小节必须写明：触发问题、结论、核实方法与证据、与原文的差异。修订涉及历史结论时，同时回改原小节并标注复核日期，避免两处结论并存。

## 配图（2026-10-13 用户要求）

**不要通篇文字。** 每份日报配 3 到 6 张图，放在它对应的那一节里。补充核实小节可以另加，不受这个上限约束。

- 图号按正文出现的先后连排，`figN` 的文件名跟着走。同日后续补写的小节如果插入到前面章节之前（比如「二·补」排在「三·补」之前），要连带重排图号、文件名和图注里的编号，不要出现先读图 5 再读图 3 的情况。

- 优先用源文档里的图。仓库 `docs/images/`、官方博客的架构图这类，下载到 `assets/<日期>/`，图注里写明出处。
- 不够就自己画。画的是正文已经写了的事实和数字，不引入新结论；图里出现的每个关系，正文都要能找到对应的话。
- 样式跟日报一致：浅色、扁平、细边框。不用渐变、阴影、emoji、外链字体。颜色只用来表达含义（该做/不该做、贵/便宜、丢失/保留），不做装饰。
- 引用写法：`![图 N：说明](assets/<日期>/figN-短名.svg)`。位图可加宽度，例如 `![图 N：说明](assets/<日期>/figN-短名.png "w=430")`。
- 站点构建（`site/build.mjs`）会把图渲染成带图注的 `<figure>`，图片一律按路径引用；正文里只写裸文件名也能解析（会在本栏目 `assets/` 下按文件名回退查找）。图注由这段说明文字直接生成，所以要能独立看懂，不依赖上下文；图里出现的数字要和正文一致。

## 发布链路

日报写完后由站点生成器统一发布，不需要手工转 HTML：

| 步骤 | 命令 |
| --- | --- |
| 重建站点 | `node site/build.mjs`（根目录下任何 `NN-名称` 目录都会自动成为一个栏目） |
| 提交推送 | `git add -A && git commit && git push origin master` |
| 部署上线 | `rm -rf .edgeone/assets && edgeone makers deploy -n moting-blog` |

线上地址：<https://blog.moting.com.cn>（Makers 项目 `moting-blog`，加速区域为全球可用区·不含中国大陆）。部署前必须先删 `.edgeone/assets`，否则构建阶段会撞上沙箱的删除拦截。

## 选材主线

以 **跨端渲染 ↔ AI 工作流编排** 的交叉带为核心，仓库轮换，避免连续重复同一方向。候选方向：

- 生成式 UI / 受约束组件渲染（json-render、OpenUI、A2UI、CopilotKit）
- 多智能体编排与工作流引擎（LangGraph、agent-framework、动态工作流）
- 流式输出与增量 patch、渲染管线
- 决策模型 / 路由与编排成本结构
- 跨平台渲染运行时与 AI 的结合

## 语言风格（2026-10-12 用户明确要求）

**说人话。**日报是给人看的，不是给人做技术评审的。

- 用短句、日常词。像跟同事讲清楚一件事，不像写方案。
- 少堆术语。「收敛」「同构」「范式」「映射」「一等公民」「稀缺资产」「影响半径」这类词，能换成大白话就换。
- 段落开头直接把事情说了，不要「结论先行：」「本质上」这种垫场。
- 不写升华句和收尾金句。讲完事实就停。
- 加粗只用在数字和关键结论上，不要每行都挂一个加粗标签加冒号。
- 破折号少用，该用逗号、句号、冒号的地方就用标点。
- 事实、数字、来源、日期、代码、路径一个都不能少，也不能改。换的是说法，不是内容。

## 真实性纪律

- 要闻逐条标注来源与发布日期；**厂商自测数据必须显式标注**，不写成既成事实。
- 厂商基准与第三方测试结论不一致时，两者都写，标注口径差异。
- 仓库分析以 GitHub **原始文件直读**为准（`raw.githubusercontent.com`）。GitHub API 可能限流 60 req/h，取不到的数据（star 数、提交时间）**留空并说明**，不推测。
- 当日无值得收录的内容时，如实说明，不凑数。
