## 一、今日要闻

### 1. 简单的判断活儿，开始从大模型里拆出来了

Agent 干活其实是循环的：模型决定下一步做什么，工具去执行，模型再看结果。问题在于每做一个决定就得调一次模型，哪怕这个决定只是"这条消息该转给谁"或者"这个输入合法吗"。又慢又贵。

现在有人专门做这块。TypeSafe AI 的 Jev 不写文字，只回三种东西：`Choice`（几个选项里挑一个，带概率和置信度）、`Score`（按等级打分，给连续分数）、`Noul`（回答是或否的概率）。底层还是 transformer，但用并行采样一次把答案全吐出来，训练方法他们自己叫 RLCD。

- 价格 $0.042 / 百万输入 token，输出不要钱。
- 厂商说最快 193.6 倍速、便宜 444.6 倍。他们自己在博客里也承认这是"实际收益里偏高的那一头"。
- 第三方测出来方向一样，幅度小很多：中位数大约快 2.0 到 3.6 倍，便宜 4.7 到 7.5 倍，准确度跟同量级小模型差不多。
- 2026-10-09 完成 8.7 亿美元 A 轮，估值 75 亿美元，a16z 领投，Sequoia、DCVC 跟投。三周前种子轮才 4000 万，估值 2 亿。公司约 25 人，2024 年成立。
- OpenAI 同期上了 Decisions API，返回的是结构化决策不是聊天消息。LangSmith LLM Gateway 已经接了，带模型回退、脱敏和花费上限。

跟你的关系：不用先动架构。翻一下日志，看你工作流里 LLM 调用都花在哪。如果大头是分类、路由、校验这类简单判断，把这些节点换成决策原语就直接省钱。常见的分法是 90% 的简单步骤走便宜模型，10% 的复杂规划留给大模型。

### 3. AI 生成界面这件事，已经从 demo 变成产品能力了

做生成式 UI 的这几家基本都在走同一条路：AI 生成受约束的 JSON，客户端照着组件目录渲染，各端各渲染各的。

- Vercel Labs 的 `json-render`（Apache-2.0）：把模型输出限制在你定义的组件目录里，边流边渲染。同一份 catalog 能出到 React、Vue、Svelte、Solid、React Native、Three.js、PDF、Email、Image（SVG/PNG）、Video（Remotion）、终端（Ink）、Next.js、TanStack Start。详见第二节。
- Thesys 的 `OpenUI`（MIT）：自己造了个紧凑语言 OpenUI Lang，一行声明一个组件，支持渐进渲染。官方说比 JSON 方案省 token，自己测的，约 2.1 倍。
- ChatGPT Intelligent UI，10-07 上付费层，10-08 上全量：对话里直接渲染滑块、图表、小计算器，不再只回一段 markdown。
- CopilotKit 的 OpenGenerativeUI（MIT）：把模型生成的 HTML/SVG 流进沙箱 iframe，用 Idiomorph 打局部补丁而不是整个重建。流式参数顺序是定死的：`initialHeight → placeholderMessages → css → html → jsFunctions → jsExpressions`。先出结构再挂行为，这样才可能边流边渲染。

跟你的关系：多端渲染器适配、节点树 diff、流式增量 patch，这正好是这条路上最难的三个地方，也正是你做过的事。转型不用从零开始，是换个地方用。

## 二、今日精选仓库：`vercel-labs/json-render`

为什么选它：它身上那条"一份描述，多端渲染"的路子你熟。而且同一套东西它同时用在跨端渲染和 AI 编排上，catalog、registry、state 这三层，跟你手上的渲染层和编排层结构很像。

### 基本信息（直读仓库文件核实）

| 项 | 值 |
| --- | --- |
| 仓库 | `https://github.com/vercel-labs/json-render` |
| 维护方 | Vercel Labs，实验产品线 |
| 许可证 | Apache-2.0，LICENSE 文件确认过，含专利授权，比 MIT 多一层保护 |
| 语言 / 工程 | TypeScript；pnpm monorepo 加 Turborepo；`node >= 24`、`pnpm >= 11`；vitest 测试；发到 npm 的 `@json-render/*` 带 `--provenance` |
| 仓库自述 | "The Generative UI framework." |
| 复核说明 | star 数和最近提交时间没拿到，GitHub API 限流了（60 次/小时），我不猜。InfoQ 2026-03 报道说当时 13,000+ stars，是二手信息，没核实 |

### 它解决什么问题

LLM 想把"回答"变成"界面"，以前只有两条路。回 markdown，表达力不够；回一段 UI 代码或者无约束 JSON，又没法控、有安全风险。

json-render 走第三条：把模型关在你定义的组件目录里。它只能用你注册的组件和动作，输出必须匹配 Zod schema。界面的表达力有了，可预测性和安全性也在。

### 它是怎么跑起来的

```
用户 Prompt → AI + Catalog → JSON Spec → Renderer
                 ↑guardrailed   ↑predictable   ↑streamed
```

1. 定义护栏 `defineCatalog(schema, { components, actions })`，每个组件的 props 用 Zod 声明。
   ```typescript
   const catalog = defineCatalog(schema, {
     components: {
       Card:   { props: z.object({ title: z.string() }), description: "A card container" },
       Metric: { props: z.object({ label: z.string(), value: z.string(),
                 format: z.enum(["currency","percent","number"]).nullable() }), ... },
     },
     actions: { export_report: { description: "Export dashboard to PDF" } },
   });
   ```
2. 生成 system prompt：`catalog.prompt()` 直接从目录里推出模型能看到的组件清单、props schema 和可用动作。护栏和提示词是同一个来源，不会各说各的。
3. 模型输出扁平 spec，下面细说。
4. 流式渲染：`createSpecStreamCompiler()` 一块一块吃模型输出，返回 `{ result, newPatches }`，UI 先拿部分结果渲染。

### 四个可以直接抄的做法

1. 扁平 spec 加引用式 children，不搞嵌套树。
   ```json
   { "root": "card-1",
     "elements": {
       "card-1":   { "type": "Card", "props": {...}, "children": ["button-1"] },
       "button-1": { "type": "Button", "props": {...}, "children": [] } } }
   ```
   为什么这点重要：不这么做就没法流式渲染。嵌套树流到一半就是棵残树，而扁平 map 能按 JSON Patch（RFC 6902）一条条往里打补丁。你在 DOM 层熟悉的那套增量 patch 思路，这里搬到了 spec 层。

2. 描述和渲染彻底分开，一份 spec 出多个端。同一个 catalog 对应 20 多个渲染包：Web 有 React、Vue 3、Svelte 5、Solid；移动端有 React Native，带 25+ 组件；3D 有 React Three Fiber，20 个组件含 GaussianSplat；另外还有 PDF、HTML Email、Image（Satori 出 SVG/PNG）、Video（Remotion 时间线）、终端（Ink TUI）、整站（Next.js / TanStack Start，带路由和 SSR）。

   这就是一个跨端渲染抽象层该长的样子。描述层（catalog + spec）和实现层（各 renderer 包）之间只靠 registry 约定的接口说话。

3. 里面塞了个小型的响应式运行时。spec 里可以直接写数据驱动的表达式：
   - `{ "$state": "/form/hasError" }` 读状态
   - `{ "$cond": …, "$then": …, "$else": … }` 按条件取值
   - `{ "$template": "Hello, ${/user/name}!" }` 插值
   - `{ "$computed": "fn", "args": {...} }` 调注册函数
   - 元素级 `visible` 控制显隐，`watch` 监听状态变化触发 action

   状态存储这块提供了适配器：Redux、Zustand、Jotai、XState。

4. Devtools 和 MCP 是内置的，不是外挂。`@json-render/devtools-{react,vue,svelte,solid}` 能看到 spec 树、改状态、翻 action 日志和流日志、浏览 catalog、从 DOM 反查是哪个组件，生产环境 tree-shake 成 `null`。`@json-render/mcp` 让 Claude、ChatGPT、Cursor、VS Code 里都能用。

### 跟你现在会的对一下

| 你已经会的 | json-render 里对应什么 | 迁移成本 |
| --- | --- | --- |
| 一套描述出多端实现 | catalog 定义加 20 多个 renderer 包 | 低，几乎同构 |
| 渲染节点树的 diff 和增量更新 | 扁平 `elements` 加 JSON Patch 流式补丁 | 低 |
| 工作流里的节点注册表和插件体系 | `defineRegistry` 加 catalog 的 components/actions | 低 |
| 状态机和响应式绑定 | `$state`/`$cond`/`watch` 加 StateStore 适配器 | 中，得先熟悉它的表达式语义 |
| 编排层的动作分发 | spec 里的 `action` 加内置 `setState` | 低 |

### 怎么上手

```bash
git clone https://github.com/vercel-labs/json-render && cd json-render
pnpm install && pnpm dev
```

仓库里现成的例子：`examples/chat`、`examples/vue`、`examples/svelte`、`examples/svelte-chat`、`examples/vite-renderers`（同一份 spec 分别用 React、Vue、Svelte、Solid 渲染，适合对照看）、`examples/react-native`（Expo）、`examples/react-three-fiber-gsplat`。

### 要注意的

- Vercel Labs 的实验品，不是稳定产品。README 没承诺版本稳定或者 API 冻结，接之前想清楚能不能接受它改 API。
- 包多。`@json-render/*` 系列 30 多个，供应链面和后续升级都要算成本。
- 环境门槛：要 `node >= 24`、`pnpm >= 11`，而且强制 `engineStrict`，老环境得先升。
- `pnpm-workspace.yaml` 里设了 `minimumReleaseAge: 2880`，新包发布 2 天内不解析。这个防供应链投毒的做法可以直接抄到自己仓库。
- 跟别的方案怎么选：要跨 agent 复用 UI、走协议互通，Google 的 A2UI 是协议层的选择；只管自己家组件集，json-render 更顺手。两者的关系我 2026-10-12 又核了一遍，见下面。

### 还没搞清楚的

1. `json-render`（Apache-2.0）和 `thesysdev/openui`（MIT）在同样界面下的真实 token 开销和首屏耗时，需要放同一套组件里实测对比。
2. `@json-render/mcp` 跟 MCP Apps、OpenAI Apps SDK 的职责边界和兼容性。
3. 扁平 spec 加 JSON Patch 跟嵌套树比，在树很深、状态更新很频繁的时候，补丁体积会不会成瓶颈。

## 二·补 补充核实：json-render 跟 A2UI 是什么关系（2026-10-12 下午）

缘由：有人问"这两个概念看着很像，json-render 是不是照着 A2UI 做的"。

结论：不是。json-render 自己的线格式是 `{ root, elements }` 这套扁平元素树，跟 A2UI 是两回事，只是结构上长得像。A2UI 在它这儿的位置是"可以承载的一种外部 schema"，不是它实现的协议。

怎么查的：把完整源码 tarball 拉下来全库搜（`codeload.github.com/vercel-labs/json-render/tar.gz/refs/heads/main`，约 1211 个 ts/tsx/json/md 文件）。

| 查什么 | 结果 |
| --- | --- |
| 全库匹配 `a2ui` 的文件 | 9 个，全是文档站资源（`content/docs/a2ui.mdx`、`adaptive-cards.mdx`、`schemas.mdx`、`custom-schema.mdx`、`changelog.mdx`、`meta.json`，加导航、标题和测试基线） |
| `packages/` 和 `examples/` 里 `a2ui` 命中数 | 0 |
| 有没有 `@json-render/a2ui` 这个包 | 没有。packages 下 34 项，没有 a2ui |
| 文档站导航里怎么摆的 | `docs-navigation.ts` 把它跟 `Adaptive Cards`、`AG-UI` 并列，归在集成指南里。前面还有 `AI SDK` 和 `Jev (Experimental)` |
| 页面自己怎么说的 | 黄色警示框原文："This page demonstrates how json-render can support A2UI. The examples are illustrative and may require adaptation for production use." |

也就是：只是文档里写了"可以这么接"，没有在维护的实现。

为什么看着像：两边被同一批要求推到了同一种形状。

| 做法 | A2UI | json-render |
| --- | --- | --- |
| 组件用扁平表加 ID 引用，不嵌套 | adjacency list model | `elements` map |
| 组件白名单放在客户端 | catalog 加 catalogId | `defineCatalog` |
| 结构、状态、渲染分成三层 | 是 | 是 |
| 用 JSON Pointer 路径做数据绑定 | `{"path": "/reservation/date"}` | `{"$state": "/user/name"}` |
| 渐进式流式渲染 | 有 | 有，SpecStream |

但它们不在一层上。

| 维度 | A2UI | json-render 原生 |
| --- | --- | --- |
| 本质 | 协议。跨信任边界的线格式，带版本号和规范 | 引擎。应用内的生成式 UI 引擎，schema 可插拔 |
| 一次传什么 | 消息序列（v0.9：`createSurface` → `updateComponents` → `updateDataModel` → `deleteSurface`），服务端到客户端单向；交互走另一条 A2A 通道的 `userAction` / `error` | 一份完整 spec 文档（`root` + `elements`），SpecStream 编译出 JSON Patch 增量 |
| 组件类型怎么写 | v0.8 是单键对象 `{"Text": {...}}`；v0.9 拍平写成 `"component": "Text"` 加同级 props | `{"type": "Text", "props": {...}}` |
| children 写在哪 | 父组件的 prop 里：`{explicitList:[...]}` 或 `{template:{dataBinding, componentId}}` | 元素自己的 `children: string[]` |
| 版本协商 | 有 `version` 字段加 `catalogId` | 没有 |
| 组件目录 | 协议自带 basic catalog，客户端可以扩 custom catalog | 完全自定义，没有标准目录 |
| 渲染器覆盖 | Lit、Angular、React、Flutter(GenUI SDK)、Markdown；SwiftUI 和 Jetpack Compose 计划 2026 Q2 | React、Vue、Svelte、Solid、RN、Three.js、PDF、Email、Image、Video、Ink、Next、TanStack |
| 传输 | 传输无关，规定 JSONL，可以走 A2A、AG-UI、SSE、WebSocket | 没有传输这回事，接什么由你决定 |
| 出处 | Apache-2.0，Google 做的，CopilotKit 和社区一起贡献 | Apache-2.0，Vercel Labs |

顺手发现那份文档有两处没跟上：

1. json-render 的 A2UI 集成页用的是 A2UI v0.8 的消息名（`surfaceUpdate`、`dataModelUpdate`、`beginRendering`），A2UI 现在稳定版已经是 v0.9.1 了（`createSurface`、`updateComponents`、`updateDataModel`、`deleteSurface`）。页面没标版本，照着做会产出旧版线格式。
2. 那页把 A2UI 叫成 "Google's Agent-to-User Interaction protocol"。Google 官方叫法是 "Agent to UI" 或者 "Agent-to-User Interface"。

怎么用：两个不是二选一，是两层。A2UI 管"线上说什么"，跨组织、跨厂商互操作的时候才有意义；json-render 管"本地怎么把这东西变成能渲染的状态和真组件"。想合起来用，就把 A2UI 的消息定义成 json-render 的一个 schema（`defineCatalog(a2uiSchema, {...})`），registry、状态适配器（Redux、Zustand、Jotai、XState）、SpecStream、Devtools 这些直接拿来当底座。只在自己 app 里用的话，A2UI 那套协议开销（版本号、catalogId、消息序列、传输绑定）就是纯支出。

证据来源：`vercel-labs/json-render` 仓库源码直读（2026-10-12 下 main 分支 tarball）｜A2UI 官方规范站 `a2ui.org` 和 Google Developers Blog 发布说明

## 二·补2 补充核实：json-render 站在渲染管线的哪一层（2026-10-12 下午）

缘由：接着上面往下问。跨端渲染常被描述成"一份指令、多端渲染"，RN 要算布局、做 diff、算出要增删哪些组件、调整哪些组件，再组装成指令下发给各端。那 json-render 下发到各端的时候，是不是也过一层适配、然后下发指令。

结论：RN 那段描述是对的，但 json-render 不在"下发指令"那一层，它站在更上面一层，给出的还是声明。

它停在哪

看 `packages/react-native/src/renderer.tsx` 就知道。核心那个 `ElementRenderer`，最后吐出来的是一棵 React 元素树：

```tsx
<Component element={resolvedElement} emit={emit} bindings={elementBindings}>
  {children}
</Component>
```

交出去就完事了。之后做布局、做 diff、算增删、组装指令的，是 React 和 RN 框架自己，json-render 一点没参与。

依赖也印证这一点：`@json-render/react-native` 只依赖 `@json-render/core`，加一个 `react-native` 的 peer，包里没有任何指令协议。

那层"适配"是什么

是 registry：把 catalog 里的 `type` 映射到本端组件。转完出来的是 React 组件、Vue 组件、Svelte 组件、RN 的 View 和 Text，全是声明。各端拿到声明后，再各跑一遍自己的 diff、自己的布局、自己的提交。

官方文档写的是，各端 renderer "turns the spec into platform-native output"。整份文档搜 yoga、layout engine、reconcil，一个都没有。它不碰这一层。

两层的 patch 别混

- 打在 spec 上的：`core/diff.ts` 的 `diffToPatches`，RFC 6902，路径是 JSON Pointer 指到 spec 内部，像 `/elements/card-1/props`。流式那套 SpecStream 也是这个，JSONL 一行一个操作。这层跨端一致。
- 打在视图上的：各端框架自己的。spec 一变，React 走它的 reconciliation，Vue 走它的，互不相干。这层不共享。

"diff 之后知道要增删哪些组件"这个动作，全在下面那层，跟 json-render 没关系。

两种模式

- RN 那种：一份指令，多端渲染。像字节码配统一运行时。能统一，是因为所有目标端都是屏幕上的原生控件，共用同一套 Yoga 布局模型。
- json-render 那种：一份描述，多套原生实现。像一份 IDL 配各端的独立实现。

它做不了统一指令层，原因也实在：目标端拉太远，DOM、PDF、SVG、视频、终端、3D 都在里面，没有共同的布局模型。硬抽一层指令，抽出来的只会是谁都不好用的最小公约数。

它统一的是"调用组件"这件事

往上退一步看，json-render 挑的抽象单元是"元素"：一个 type、一组 props、一份 children 引用。这个单元在每一端都得能找到对应物才能跑，React 里是组件，PDF 里是打印元素，终端里是 Ink 组件。

抽象挑得高，才铺得开。要是它挑低一层去统一布局盒模型，那 Web 和 RN 能跟上，PDF 和终端当场出局。

那它该叫什么

聊到这儿有人接着问："这么说，json-render 是用来适配渲染框架的框架？"

方向对了一半。它确实架在 React、Vue、Svelte、RN 这些框架**上面**，自己不渲染，"框架之上的框架"这层属性成立。但"适配"这个词把重心放反了。

先把它的两个职责拆开：

- 上游：把 AI 吐出来的自由文本，压成一份能被 Zod 校验、能流式、能增量打的格式。这是第一职责。
- 下游：把这份格式映射到各家框架的组件上。跨端渲染是这份格式做出来之后**顺带**得到的能力，不是它的起点。

"适配"一般指 adapter，A 转 B，一对一翻译。json-render 不是这个模式。它的做法是先定一份中立格式，然后让每一端自己写一个消费者来读它。这更像编译器里的 IR，或者 OpenAPI：OpenAPI 也不是"用来适配各种语言的框架"，它是先定一份描述，各语言各自生成 client。json-render 是同一个路子，只是它的前端不是手写 YAML，是 AI 生成。

落到代码上就三块：`catalog` 定"能说什么"，`spec` 装"说了什么"，`registry` 是每端自己写的那个"怎么把它变成本端组件"。真正干活的是各端框架自己。

所以准确的说法是：它是给 AI 的输出定格式、顺带能喂给多个渲染框架的中间层。不是转接头，是通用格式加各端各自的插座。

证据来源：`vercel-labs/json-render` 仓库源码直读（2026-10-12 下 main 分支 tarball，`packages/react-native/src/renderer.tsx`、`packages/core/src/diff.ts`、`apps/web/content/docs/streaming.mdx`、`apps/web/content/docs/renderers.mdx`）

## 二·补3 补充核实：多端一致性到底靠什么保证（2026-10-12 下午）

缘由：读完上面的层次分析，有人接着问："那它只统一 UI 输出的描述，渲染成什么样看下游适配器吧？一致性咋样？"

结论分两半。它统一的不只是描述，还有一整套运行时语义；但组件和外观这层完全靠下游自觉，而且已经漂了。

它统一的不只是"描述"

除了结构，它还统一了一套运行时语义：`$state`、`$bindState`、`$cond`、`visible`、`repeat`、`on` 加 actions。

这部分是**共享代码**，不是各端各写一遍。每个端的 renderer 都 import core 里同一批函数（`resolveElementProps`、`resolveBindings`、`evaluateVisibility`、`resolveActionParam`、`diffToPatches`）。所以"绑定怎么解析、条件怎么算、动作参数怎么取"在每一端是同一份实现。

"渲染成什么样看下游适配器"这句话，对外观和组件是成立的。

一致性分四层，实测差很多

| 层 | 一致性 | 实测证据 |
| --- | --- | --- |
| 运行时语义 | 高 | 各端共用 core 纯函数，一次实现多端复用 |
| spec 结构 | 已漂移 | 各端各复制一份 `schema.ts`。`slots` 字段 react / vue 有，svelte / solid / react-native 没有 |
| 内置动作 | 已漂移 | `builtInActions`（setState / pushState / removeState / validateForm）只有 web 系有，RN 端没有 |
| 组件契约 | 无保证 | react 包一个内置组件都没有；react-native 自带 26 个（Container / Row / Column / SafeArea / Pressable 等） |
| 给 AI 的 prompt | 各端定制 | RN 端塞满 TAB NAVIGATION、SCREEN NAVIGATION（push / pop）、FIXED BOTTOM BAR；web 端塞 NAMED SLOTS、FILTERED LISTS、表单校验 |
| 视觉外观 | 零保证 | 各端组件各写各的样式 |

中间那三行最要命：同一份 catalog，Web 端和 RN 端承认的字段和组件都不一样。

测试网只盖了一个字段

全库唯一的跨端一致性测试是 `packages/core/src/repeat-schema-parity.test.ts`。它遍历 9 个端的 schema，然后只断言一件事：`repeat` 字段是 optional 的 any。

各端的测试文件数：

```
react 11   solid 8   vue 7   svelte 6   react-native 0
```

RN 端一个测试文件都没有。也没有任何跨端渲染快照对比。

所以结论

一致性靠"约定 + 共享 core"，不靠编译器强制。语义层因为共享实现是真的稳；组件层和 prompt 层全靠各端自觉，漂移已经发生，还能测出来。

这是跨端方案的经典陷阱：共享的抽象层保住了，越往下游越容易各走各的。json-render 把最容易被写歪的那部分（绑定、条件、动作解析）收进了 core，这点做对了，但它没建那层能强制各端对齐的东西。

要真拿它做多端，得自己补一张契约测试网：同一份 spec 跑所有目标端，比对输出树或渲染结果。不然今天 `slots` 缺一个、明天组件 props 改一个，不会有任何提示。

证据来源：`vercel-labs/json-render` 仓库源码直读（2026-10-12 下 main 分支 tarball，各端 `packages/*/src/schema.ts` 逐文件 diff；`packages/core/src/repeat-schema-parity.test.ts`；`packages/react-native/src/catalog.ts`）

## 三、今天可以动手的三件事

1. 先量自己的账。统计现有工作流里 LLM 调用都在干什么，路由、分类、校验、生成各占多少，估算一下把"简单判断"换成决策原语能省多少、会慢多少，再决定第 1 条要不要试。
2. 用 catalog 的思路回头看看自己的渲染层。你那套"渲染描述"是不是已经能约束、能流式、是扁平的？不是的话先把这步做了，这是接任何生成式 UI 方案的前提。
3. 列一张 Agent 权限表。每个 Agent 能不能联网、能不能写外部系统、能不能替你对外提交内容，都写清楚。第 2 条里那两件事，一个是千级并行放开，一个是模型自己编造内容提交给警方，说明这张表现在得有。
