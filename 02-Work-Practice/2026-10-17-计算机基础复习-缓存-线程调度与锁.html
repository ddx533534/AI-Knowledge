二、缓存局部性：重复访问与相邻访问

2.1 时间局部性与空间局部性

类型访问特点例子
时间局部性刚访问过的数据，很快再次访问循环反复使用同一个值
空间局部性访问一个地址后，很快访问附近地址顺序扫描连续数组
for (int i = 0; i < a.length; i++) {
    sum += a[i];
}

sum 的重复使用体现时间局部性，实际可能一直在寄存器中；连续数组的 a[i]、a[i+1] 体现空间局部性。只扫描一遍、每个元素只访问一次时，对数组元素本身没有明显的时间局部性，但仍可利用空间局部性。

数组大于缓存，不等于缓存没有用。程序可以一条缓存行一条缓存行地使用数据，无须整个数组同时留在缓存里。缓存模型与局部性可参照 OSTEP 内存访问与缓存讨论。

2.2 一次未命中加载整条缓存行

练习假设：元素 8 字节、缓存行 64 字节、起始地址对齐、缓存开始为空、忽略预取，期间没有其他访问造成相关行被替换。64 字节是本题参数，不是所有处理器的统一常量。

一条行装 64 ÷ 8 = 8 个元素。顺序读前 16 个：

读取位置过程结果
a[0]加载包含 a[0]～a[7] 的行未命中
a[1]～a[7]数据已一起带入7 次命中
a[8]加载包含 a[8]～a[15] 的行未命中
a[9]～a[15]数据已一起带入7 次命中

总计 2 次未命中、14 次命中；只读前 8 个则是 1 次未命中、7 次命中。起初回答“8 次命中、8 次未命中”，纠正点是第一次未命中就把邻近 7 个元素一起带入。

若只读 a[0]、a[8]、a[16]、a[24]，四次访问落在不同的行，在上述冷缓存模型中都未命中。四条行仍保留时，再次读取 a[0] 会命中，体现时间局部性。

2.3 缓存行对应内存地址，不按变量依赖拼装

起初疑问：x 计算需要 z，加载 z 会不会把同一行中的 y 覆盖？

缓存行对应一段固定、连续、对齐的内存地址范围。x、y 是否同一行由地址决定，不由业务依赖决定。若 z 位于远处另一段内存，它属于另一条行；不会因为 x 依赖 z，就把 z 拼进 x、y 的这条行中。

缓存空间有限，加载新行可能替换旧行，但这是缓存副本的替换，不是任意改写变量 y 的值。脏数据按一致性和写回等机制处理；具体行为取决于缓存架构。计算依赖与地址相邻是两件事。

三、伪共享：不同变量也可能争夺同一条缓存行

假设线程 A 只写 x、线程 B 只写 y，彼此没有业务依赖，分别运行在不同核心上，但 x、y 位于同一条缓存行。频繁交替写入可能引起缓存行所有权迁移与副本失效，增加开销。

核心 A 写 x → 获得所在行的写权限
核心 B 写 y → 又需要同一行的写权限
核心 A 再写 x → 可能再次发生一致性协调

这叫伪共享。它主要是性能问题，并不自动等同于程序数据竞争；若业务上也有冲突访问，则还需另行处理正确性。所有线程只读、没有写入时，不存在这里由交替写入导致的伪共享开销。Linux 内核：False Sharing

缓存里“以前有这个数据”不代表现在仍可直接使用，副本还必须有效，写入还需所需权限。把 x、y 分散到不同缓存行，可以缓解这两个变量之间的伪共享，但不能替代业务同步。该布局也可能增加占用，应以实际性能验证为依据。

本轮表现：能够解释独立变量分行后减少写权限争夺；缓存内容、缓存槽位与变量内存值的区分仍建议间隔复测。

四、线程调度：就绪、运行与阻塞

4.1 并发不等于并行

并发是在一段时间内多个任务交替或重叠推进；并行是同一时刻确实执行多个任务。讨论单 CPU 调度时，采用“一个逻辑 CPU”的前提。支持 SMT 的一个物理核心可能暴露多个逻辑 CPU，不能把物理核心和逻辑 CPU 混为一谈。

线程与进程一样，能用运行、就绪、阻塞等抽象状态理解调度；它们不是 Java Thread.State 枚举的逐项对应。尤其 Java RUNNABLE 包含运行及等待处理器资源等情况。OSTEP 线程入门、Java Thread.State

状态含义
运行正在 CPU 上执行
就绪已具备运行条件，等待调度
阻塞／等待等待 I/O、锁或条件等，暂不能继续相应执行
A 运行 → 等网络，进入阻塞
B 已就绪 → 调度执行 B
A 数据到达 → A 就绪
调度器选中 A → A 运行

数据到达不意味着马上运行。调度策略可能让 A 继续等待，也可能发生抢占；不能单凭 B 的时间片未耗尽断言 A 绝不会抢占。

4.2 阻塞等待不等于 CPU 空转

A 阻塞等网络时，不占着逻辑 CPU 执行，系统可以运行 B。没有可运行工作时，CPU 才可能空闲。反复执行循环检查“数据到了没有”则属于忙等，会消耗 CPU。

A 此刻等待 I/O，不足以证明整个任务是 I/O 密集型；B 就绪也不等于它必然是 CPU 密集型。分类要看主要时间花在计算还是等待。

4.3 上下文切换保存执行现场

从 B 切换到 A，需要保存 B、恢复 A 的相关执行状态，包括程序计数器、栈指针和通用寄存器等。局部值可能位于寄存器或栈中；调用栈通常保留在内存，无须每次复制整份栈。

切换还可能影响缓存命中表现，但不是每次都必须重新加载全部缓存。上下文与线程资源共享的基础说明见 OSTEP 线程入门。

五、多线程为什么不一定更快

条件可能表现
一个逻辑 CPU，纯计算任务从 2 线程增至 100无法凭空增加计算资源，可能增加调度、切换与管理开销
多线程争用共享资源可能等待、阻塞、重试或发生缓存一致性开销，不一定每个线程都阻塞
多个独立任务主要在等 I/O请求等待可以重叠，缩短总体完成时间
多个可用核心，可拆分计算任务可能通过并行计算加速，收益受串行部分与协调开销限制

I/O 场景不要求固定“一个线程请求、一个线程计算”。每个线程都可以执行请求、等待、处理结果，多个请求的等待阶段重叠。I/O 完成后的线程仍需调度，不保证立即处理。

这些是条件化判断，不是性能测试结论。今天最后能独立说明上下文切换、资源竞争和 I/O 等待重叠；多核计算的并行收益由辅导补充，下次再复测。

六、sleep、wait 与通知：让出 CPU 不等于释放锁

6.1 三类操作的区别

操作监视器锁行为继续执行的条件
Thread.sleep不释放已经持有的监视器锁休眠结束／被中断后按相应语义继续，还受调度影响
lock.wait释放 lock 的监视器；不会自动释放其他对象的锁正常返回前必须重新获得 lock
lock.notify / notifyAll通知等待线程，不释放当前持有的 lock当前持有者释放后，被通知线程才有机会重新取得锁

wait、notify、notifyAll 要由拥有对应监视器的线程调用，否则会出现 IllegalMonitorStateException；wait 还可能被中断，需要处理 InterruptedException。Object API、Thread API

6.2 通知不等于立即运行，也不保证公平

B 在 synchronized(lock) 内 notify 后，仍可以继续执行自己的代码；A 不能立即进入同一个监视器保护的区域。notify 选择哪个等待线程，Java 不保证按等待时长或优先级；notifyAll 通知所有，也不保证等待最久者先拿锁。

必须区分“从等待集中被选中”“竞争监视器”“获得执行机会”，不是 CPU 硬件根据 Java 业务规则选择通知对象。Object.notify / notifyAll

6.3 为什么条件等待使用 while

下面是演示片段：queue 与 lock 已安全交给线程，所有队列访问使用同一把锁；方法把中断继续向上抛。实际业务中的消费处理是否放锁内，应按一致性和持锁成本另行设计。

void consumeOne() throws InterruptedException {
    synchronized (lock) {
        while (queue.isEmpty()) {
            lock.wait();
        }
        consume(queue.remove());
    }
}

wait 返回时，队列可能已被另一个消费者取空；也可能发生虚假唤醒。while 会重新检查条件，if 则不会回头判断，可能直接从空队列取数据。三个消费者被通知、只有一个元素时，先拿锁者取走，后续消费者拿锁发现空，再次 wait 并释放锁。JLS §17.2

6.4 同一把锁提供互斥与可见性

全部队列读写遵守同一把 lock 时，不必仅为这些访问的可见性给 queue 引用额外加 volatile。前一个线程解锁前的写入，对随后获取同一把锁的线程可见。引用加 volatile 不会自动让队列内部 add/remove 线程安全。JLS §17.4.5

两段代码各自有 synchronized，但用的是不同锁，不能据此保证同一个 count++ 互斥，也不能依靠同一监视器的解锁／加锁规则建立相应可见性。某次结果碰巧正确，不等于实现有正确性保证。

本轮最后能够独立说出“互斥＋可见性”，并明确不同锁无法保护同一计数器的完整读改写；等待通知的公平性与虚假唤醒仍需间隔复测。

七、死锁、活锁与饥饿

现象核心表现本次示例
死锁相关线程互相等待，无法推进A 持锁 1 等锁 2，B 持锁 2 等锁 1
活锁线程持续动作、退让或重试，但没有实际进展各拿一把锁，另一把拿不到便释放，反复同步重试
饥饿系统中其他线程在推进，个别线程长期得不到服务某线程持续参与竞争，却总拿不到资源

发生几次重试、最终完成，属于正常竞争，不能只凭重试认定活锁。死锁也不能等同于所有线程都处于 Java BLOCKED，具体等待状态取决于机制。

活锁中的随机退避可以降低同步碰撞概率，但不自动提供严格进展保证。三种现象的概念对照见 Oracle 并发教程：Liveness。

统一顺序的推导：A 拿到锁 1 时，B 在锁 1 上等待，还没有拿到锁 2；A 可以继续取得锁 2，完成后释放。这里假设 A 持有锁 1，直到相关两锁操作完成，不是 A、B 同时持有同一把锁 1 后再竞争锁 2。

只要一条可能并发执行的相关路径仍按锁 2 → 锁 1 获取，就不能保证避开该循环。统一顺序针对这些锁消除这类循环，不证明整个复杂程序绝无其他死锁。

十、补充复盘：组合数、联合概率与条件概率

补充日期：2026-10-17。来源是本次混合笔试答卷与交卷后的讲解。重点是先数清等可能情况，再确定已知条件缩小了哪个范围。以下数值由题设直接推导，不是外部测量数据。

10.1 组合数：不计顺序地选取

从 n 个不同对象中选 k 个，不计选取顺序，写作 C(n,k)，也常记作上下排列的组合符号。0 ≤ k ≤ n。

C(n,k) = n! / [k! × (n-k)!]

n! = n × (n-1) × … × 1
0! = 1

先数有顺序的取法，再除掉同一组内部重复的排列：

C(4,2)  = (4 × 3) / (2 × 1) = 6
C(5,3)  = (5 × 4 × 3) / (3 × 2 × 1) = 10
C(10,3) = (10 × 9 × 8) / (3 × 2 × 1) = 120

白球 1、2 与白球 2、1 是同一组球，只计一次。虽然颜色相同，每个球仍是不同实体，可以临时编号辅助计数。

“1 白 2 黑、2 白 1 黑、3 白”是颜色分类，不是三个等可能结果；每一类包含的具体球组数量不同。只有确定基本结果等可能时，才能直接用有利结果数除以总结果数。

10.2 联合概率：A 和 B 同时发生

P(A ∩ B) 表示 A、B 同时发生。乘法公式为：

P(A ∩ B) = P(A) × P(B ∣ A)    当 P(A) > 0
         = P(B) × P(A ∣ B)    当 P(B) > 0

若 A、B 独立：
P(A ∩ B) = P(A) × P(B)

不能看到“同时发生”就直接把边缘概率相乘，独立性必须有依据。不放回抽样通常存在依赖：抽走一个白球后，下一次抽白球的概率会变化。

例如，独立尝试每次成功概率 1/2，S 表示成功、F 表示失败：

P(FFS) = 1/2 × 1/2 × 1/2 = 1/8

这里数的是“前两次失败且第三次成功”这一完整过程。

10.3 条件概率：已知 B，再问 A

P(A ∣ B) = P(A ∩ B) / P(B)    要求 P(B) > 0

分母是所有满足 B 的情况；分子是在这个范围内还满足 A 的情况。联合概率与条件概率问的是不同问题：

问法含义
A 和 B 同时发生在原样本空间中找交集
已知 B 发生，再问 A先把范围缩小到 B，再看其中有多少属于 A

若 A 一定蕴含 B，则 A ∩ B = A，此时可写成 P(A) / P(B)。一般情况下不能直接如此简化。

10.4 抽球题：至少一个白球，不是先抽走一个白球

题设：6 黑、4 白，等机会不放回抽取 3 个。设 A 为恰好 2 白，B 为至少 1 白。

先数总球组，再按条件筛选：

所有三球组合：
C(10,3) = 120

不符合 B 的全黑组合：
C(6,3) = 20

符合 B 的组合：
120 - 20 = 100

恰好 2 白 1 黑：
C(4,2) × C(6,1) = 6 × 6 = 36

P(A ∣ B) = 36 / 100 = 9/25

每一种白球二元组合都能搭配 6 个黑球，所以目标组合数是乘法。已经按不计顺序的球组计数，不再乘“白白黑、白黑白、黑白白”的顺序数，否则会重复计算。

原答卷的 4/9 不成立。把条件“至少 1 白”改成“已经取出 1 白，再从 9 个球中抽”改变了抽样过程；后面固定使用 2/3 和 1/3 相乘，也忽略了不放回抽样中数量会继续变化。

10.5 有限次尝试：到第三次不等于第三次成功

每次独立成功概率 1/2，首次成功即停止，最多尝试 3 次。T 表示实际尝试次数。

T对应完整路径概率
1S1/2
2FS1/4
3FFS 或 FFF1/8 + 1/8 = 1/4

第三次无论成功还是失败，都会停止。因此 P(T=3) 只要求前两次失败，不必再乘一次成功概率。

P(第三次成功且尝试三次) = P(FFS) = 1/8

P(最终成功 ∣ T=3)
  = P(FFS) / [P(FFS) + P(FFF)]
  = (1/8) / (1/4)
  = 1/2

原答卷把两个问题都写成 1/8。口述已能指出第三次可能成功或失败，但公式没有把这两条路径都算进分母。优先练习“联合概率”和“给定条件后的概率”的区分。

10.6 离散期望与概率自检

离散随机变量的期望，是各个可能取值乘以对应概率，再求和：

E[X] = Σ x × P(X=x)

E[T] = 1 × 1/2 + 2 × 1/4 + 3 × 1/4
     = 7/4
     = 1.75 次

原答卷漏答期望小问。计算前后检查：

  • 所有互斥、穷尽的取值概率之和应为 1；本题 1/2 + 1/4 + 1/4 = 1。
  • 概率应在 0 到 1 之间；条件分母必须非零。
  • 本题 1 ≤ T ≤ 3，所以期望也应在 1 到 3 之间。
  • “第三次达到上限仍失败”不能漏算。

12.1 最少处理实例：堆里必须保存更新后的结束时间

题意：给定任意顺序的任务区间 [start,end)，一个实例同一时刻只处理一项任务；结束时刻等于下一任务开始时刻时允许复用。返回完成全部任务需要的最少实例数。任务数最多 100,000，空输入返回 0。

按开始时间排序，用最小堆保存每个已分配实例最后一项任务的结束时间。最早结束的实例若已经空闲，就复用；否则新增一个实例。

堆顶状态动作为什么
最早结束时间 ≤ 当前开始时间弹出旧结束时间，插入当前结束时间至少一个实例可复用，实例总数不变
堆空或最早结束时间 > 当前开始时间插入当前结束时间已分配实例均不能接当前任务，必须新增

这里堆保存已分配实例的最新结束时间，不是每一步只保存活动任务；因此可每次只复用一个实例，最终堆大小就是分配总数。

原错误是复制出整数后只改局部变量：

let mut top = heap.peek_mut().unwrap().0;
top = jobs[i][1]; // 没有更新堆中的元素

虽然调用 peek_mut，取出的 i64 仍是复制值。重新提交改为 pop 后 push，真正更新了堆。

[[0,1],[1,10],[2,3]]212
三个 [0,5]333

复杂度：时间 O(n log n)，空间 O(n)。原提交在 3,616 个小输入中有 441 个失败；重交修正后相同范围 0 失败。这个错误与前面“复制的局部值不会随原对象变化”的知识点有关，但并不是并发问题。

12.2 一次免费通行：最优状态包含券是否使用

题意：非负费用网格，从左上到右下，只能右移或下移。每个经过格子都计费，含起终点；最多用一次券，将一个经过格子的费用变为 0。网格最多 500×500，单格费用最多 10,000。

用户独立建立的两个状态成立：

状态含义
dp[i][j][0]到当前位置，券已用掉的最小费用
dp[i][j][1]到当前位置，券还没用的最小费用

初始化为 dp[0][0][0] = 0，dp[0][0][1] = grid[0][0]。已用券状态的来源：前面已使用则当前付费；前面未使用则当前免单。未用券状态必须当前付费。

used(i,j) = min(
    used(上) + cost,
    used(左) + cost,
    unused(上),
    unused(左)
)
unused(i,j) = min(unused(上), unused(左)) + cost

起点也可免单。所有费用非负，至少使用一次不会比不用更差，所以返回已使用状态可满足“最多一次”。

十三、图建模到底在做什么

把两个组看作两间教室，group 是座位表，neighbors 是每个人“不能同室”的名单。边表示限制，不是把两端组成一组。

group[v] = -1：还没安排
group[v] =  0：教室 A
group[v] =  1：教室 B

从任意未安排者开始选 A，然后沿名单传播：邻居必须放另一边。以 [[0,1],[1,2]] 为例，0 放 A，1 必须 B，2 必须 A；[0,2] 同组允许，因为两者没有冲突。若再加 [2,0]，则出现同组冲突，无解。

DFS 的白话过程是“安排完一个人，继续看他的冲突名单，处理完再回到原名单”。有双向边 0→1→0 时，从 1 看回 0，0 已有组别，只检查异组而不再次递归。因此 group 同时承担组别与已访问标记。

代码动作对应含义
外层扫 0..n，跳过已经分组者一片关系处理完，再找下一片或孤立任务
group[root]=0这一片任取起始方向，组名本身没有优先级
group[neighbor]=1-group[target]冲突邻居必须异组，仅适用于已确定为 0、1 的组别
邻居已有组别且与当前同组检出矛盾，立即返回 false
已分组邻居异组约束满足，不重新分组或递归

Rust 的 ! 对 bool 是逻辑取反，对整数是逐位取反；不能拿 !group 实现 0、1 互换。已知组号为 0 或 1 时，可用 1-group 或 group^1；-1 未分组状态不能直接转换。

二分图判定适用于两个选择、边两端必须不同的约束。若改为三组，不能继续套同一规则；一般依赖图、可达性等也会用图遍历，但不是所有图问题都属于二分染色。该知识点本轮经多次引导与参考代码后理解，尚未独立实现无递归版本，不能标为已独立掌握。

下面四个函数是助手整理并另外验证的参考实现，便于复盘；不是把用户原提交替换后声称全通过。最少实例版与用户重交同一策略；网格版修正两个哨兵；区间版规整循环；分组版改为显式栈，避免递归深度风险。

use std::cmp::Reverse;
use std::collections::{BinaryHeap, VecDeque};

pub fn min_workers(mut jobs: Vec<Vec<i64>>) -> usize {
    jobs.sort_unstable_by_key(|job| job[0]);
    let mut heap = BinaryHeap::<Reverse<i64>>::new();
    for job in jobs {
        if heap.peek().is_some_and(|end| end.0 <= job[0]) {
            heap.pop();
        }
        heap.push(Reverse(job[1]));
    }
    heap.len()
}

pub fn min_cost_with_pass(grid: Vec<Vec<i64>>) -> i64 {
    let (m, n) = (grid.len(), grid[0].len());
    let inf = i64::MAX / 4;
    // [0]：券已经用掉；[1]：券还没用
    let mut dp = vec![vec![[inf; 2]; n]; m];
    dp[0][0] = [0, grid[0][0]];
    for i in 0..m {
        for j in 0..n {
            if i == 0 && j == 0 { continue; }
            let up = if i > 0 { dp[i - 1][j] } else { [inf; 2] };
            let left = if j > 0 { dp[i][j - 1] } else { [inf; 2] };
            let cost = grid[i][j];
            dp[i][j][0] = (up[0] + cost)
                .min(left[0] + cost)
                .min(up[1])
                .min(left[1]);
            dp[i][j][1] = up[1].min(left[1]) + cost;
        }
    }
    dp[m - 1][n - 1][0]
}

pub fn longest_stable(values: Vec<i64>, limit: i64) -> usize {
    let mut high = VecDeque::<usize>::new();
    let mut low = VecDeque::<usize>::new();
    let (mut start, mut best) = (0, 0);
    for end in 0..values.len() {
        while high.back().is_some_and(|&i| values[i] <= values[end]) {
            high.pop_back();
        }
        high.push_back(end);
        while low.back().is_some_and(|&i| values[i] >= values[end]) {
            low.pop_back();
        }
        low.push_back(end);
        while values[*high.front().unwrap()] - values[*low.front().unwrap()] > limit {
            if high.front() == Some(&start) { high.pop_front(); }
            if low.front() == Some(&start) { low.pop_front(); }
            start += 1;
        }
        best = best.max(end - start + 1);
    }
    best
}

pub fn can_split(n: usize, conflicts: Vec<Vec<usize>>) -> bool {
    let mut neighbors = vec![vec![]; n];
    for edge in conflicts {
        let (a, b) = (edge[0], edge[1]);
        neighbors[a].push(b);
        neighbors[b].push(a);
    }
    let mut group = vec![-1i8; n];
    let mut stack = Vec::new();
    for root in 0..n {
        if group[root] != -1 { continue; }
        group[root] = 0;
        stack.push(root);
        while let Some(target) = stack.pop() {
            for &neighbor in &neighbors[target] {
                if group[neighbor] == -1 {
                    group[neighbor] = 1 - group[target];
                    stack.push(neighbor);
                } else if group[neighbor] == group[target] {
                    return false;
                }
            }
        }
    }
    true
}
