# Recce 渲染规划两年复盘

核实日期：2026-10-13。所有材料均在同日通过学城 CLI 直读原文核对，未引用二手转述。

## 写在开头：这两年真正长出来的是什么

**一句话结论：不是补齐了多少属性，而是这个团队两次给自己划边界，而第二次划的方式变了 —— 清单失控时换参照物，清单做完时换对照面。**

- **第一次，把模糊的问题变成可数的清单。** 25 规划的起点是一句抱怨——「属性支持度不够，业务临时来要会排期紧张」——这句话里没有一个可执行项；它的落点却是两个都算过钱的方案：按业务方代码反推缺 24 项、约 144PD，直接对齐 RN 全集缺 178 项、600PD。选了前者，并把没选的那个留在表里。从「不够用」到「缺 24 项」，是整件事由模糊变清晰的临界点。手法值得单独记：**清单大到做不完时，不是更努力地做完它，而是换一个更锋利的参照物，把清单重新切一遍。** 178 项按「RN 文档列了什么」切，24 项按「业务方代码真的用了什么」切，同一个问题规模差七倍。
- **第二次，承认清单有尽头。** 26 规划把口径从「补够用」改成「以 RN 为基线，补其短板，探其边界」，目标写成 157 项、各组件从 50%~62% 提到 100%。真正的方法论进步不在这句口号里，而在于它同时承认补完清单不等于没有问题，把目标从「清单清零」换成了「建一套能持续发现问题的机制」——前者有终点，后者没有。样板也已经做出来了，只是被放进了暂停状态：差异扫描逐文件对读 Recce 与 RN 的 Android 源码，一次捞出 14 条高置信 bug，其中 `snapToAlignment` 在属性表上是绿的，但在 `flingAndSnap` 里根本没参与计算，三种对齐方式全部失效——**它换的不是努力程度，是对照面：从「RN 的文档」换成了「RN 的源码」。**

这两件事不是二选一，是同一件事的先后：不先把边界划清楚，就没有「已知清单」这个基数，也就无法定义什么是「未知」。反过来，只做第一步会掉进一个陷阱——背景重构那 14 条里，9 条是 QA 或开发在真实业务里撞出来才登记的，没有一条是靠属性清单推出来的。

> 清单失控时，换参照物；清单做完时，换对照面。

| 词 | 意思 |
| --- | --- |
| 补齐 / 对齐 | 补齐＝新增 Recce 不支持的属性；对齐＝属性已支持但行为与 RN 不一致，把它改过来。成本结构与验收方式完全不同，两年里分在两张表里排期 |

## 一、两年的问题定义变了

25 规划的起点是「属性支持度不够，业务临时来要会排期紧张，且影响 Recce 其他渲染工作进度」，落成三条目标：集中补齐新增属性、已有属性与 RN 对齐、制定 RN Changelog Fixed 同步机制。

26 规划把起点换成一句自问自答：

> Q：Recce 渲染要做成什么样子？对比现在缺少了哪些能力？怎么去更好地实现这些能力？
> A：如果要完全对标 Web 那样的渲染能力，恐怕不是很现实……以 RN 为基线，补其短板，探其边界。即不追求 Web 全集，追求在 Native 约束下的最优解。后续进行自绘制开发时，再去打破这个约束。

从「补够用的属性」到「承认边界、只求 Native 约束下的最优解」，是这两年最大的一次口径变化。两个直接后果：补齐从「按业务代码反推、够用就行」改成「按需全部支持完」（157 项，各组件从 50%~62% 提到 100%）；「已有属性对齐」升级成「三端渲染一致性」，验收对象从 RN 换成 iOS / Android / 鸿蒙三端。

## 二、逐个方向走了一遍

### 2.1 基础属性补齐：口径从「业务反推」走到「按需全量」

25 规划的主线，也是唯一一个两年都在做的方向。

| 组件 | 2025 现状（RN 0.72 全集） | 2025 目标（口径一） | 2026 现状（仅 native prop） | 2026 目标 | 26 规划标的状态 |
| --- | --- | --- | --- | --- | --- |
| 通用布局 | 93%（52/56） | 100%（56/56） | 100%（56/56） | — | ✅ |
| 通用阴影 | 0%（0/4） | 100%（4/4） | 100%（4/4） | — | ✅ |
| ScrollView | 44%（27/61） | 52%（32/61） | 52%（38/59） | 80%（49/59） | 🚧 |
| Image | 48%（24/50） | 58%（29/50） | 53%（16/30） | 53%（16/30） | ✅ |
| Label | 46%（31/69） | 50%（34/69） | 40%（17/42） | 88%（37/42） | 🚧 |
| View | 48%（46/94） | 51%（48/94） | 未填 | 未填 | 🚧 |
| Input | 53%（41/67） | 62%（42/67） | 未填 | 未填 | 🚧 |

25 规划给两个口径都算了成本：口径一缺 24 项、约 144PD；口径二缺 178 项、600PD、平均 200PD/端。选了口径一，理由（贴近具体业务、工作量小）与代价（不能百分百保证未来需要某些奇特属性）都写在正文里。优先级按业务紧急程度切，近期要用的通用布局与阴影定 P0、其余 P1，三端 owner 明确到人。**分母这件事两年里都没定死，所以前后不能横着比。**

![图 2：同一批组件在 2025 与 2026 两份规划里的属性支持数对照](fig2-denominator.svg)

比分母更值钱的，是 26 规划新增的那一列「RN 实现层」——它把「RN 文档里列了这个属性」和「这个属性需要 native 实现」拆开了，于是大量条目判「否」，而不是继续往 native 侧堆工作量：

- Image 专表 30 项里未支持的 14 项全部判「不需要支持」：`defaultSource`、`loadingIndicatorSource`、`onProgress` 是「属性鸡肋」，`src` 是「source 已有」，`crossOrigin`、`referrerPolicy` 可以走 headers，`resizeMethod` 一族因为「recce 用 picasso、rn 用 fresco，两套图片机制」。
- ScrollView 专表把 11 个非 native prop 逐条写了 JS 层怎么实现：`stickyHeaderIndices` 是遍历 children 把子节点包成 `ScrollViewStickyHeader`；`refreshControl` 在 iOS 是当子节点放进去、在 Android 是包裹 ScrollView；`onContentSizeChange` 是转 `onLayout` 出来的。

这一列把「对齐 RN」从一个无底洞变成了一个有边界的清单，也是 2.2 里那些「不采纳」结论的方法基础。

2026 年这条线换了组织形式——不再是规划里的一张总表，而是每个组件 / 样式一份专表，标题带状态前缀，统一挂在 1.35 需求下，共 7 份（View 那份含 Props 与 Style Props 两张表）。实际状态是 Image、Shadow 收口，**View 与 ScrollView 今年也已经对齐**，但这两份标题至今仍写【对齐中】。Label、Layout、TextInput 标【暂停】，其中 Label 那份只有标题、没有结论。

![图 3：1.35 那一批组件属性专表的状态、属性数与卡点](fig3-align-board.svg)

专表比总表更有用的地方，是它把「不支持」拆成了性质不同的几类，解法完全不一样：

- **上游压根不是 native prop**——判否的主要依据，也是省下工作量最多的一类。`aria-*` 全系 11 项判「没必要，有等价属性」，`collapsable`、`testID`、`id`、`nativeID` 判「框架已有能力支持」。
- **目标平台没这个能力**——View 的 11 项无障碍属性全部判否，理由都是同一条「鸿蒙不支持无障碍」。这类不是「不做」，是做了也没有落点。
- **依赖别的工作**——`hitSlop`、`pointerEvents`、`focusable`、`tabIndex` 与 10 个 `onResponder*` 都判「需要，但依赖触摸事件重构，本期不支持」。这解释了 1.35 里为什么触摸事件重构排 P0、属性对齐只排 P1。
- **剩下才是真工作量**——View 侧 23＋15 项、ScrollView 侧 10 项 native 加 10 项待 recce-ui 配合、TextInput 侧 33 项、Layout 侧 20 项。

这批专表也顺带补上了 26 规划总表里 View、Input 两行留空的问题。

### 2.2 已有属性对齐：逐属性 diff，对的是 RN 的语义而非实现细节

25 规划把这件事排进了月表：2 月 View 与 Image、3 月 Input 与 Label、4 月 ScrollView 与 HorizontalScrollView，基线 RN 0.72.0。做法是逐属性 diff，每条给「采纳 / 不采纳」加影响面，不采纳的也给理由。判例最能说明这套方法：

| 属性 | 差异 | 结论 |
| --- | --- | --- |
| `caretHidden` / `keyboardType` | 新版修了小米 Android 10 上的 crash | 机型兼容性修复，采纳 |
| `secureTextEntry` | value 为 true 时只清 `TYPE_TEXT_VARIATION_VISIBLE_PASSWORD` 一个标志位，而不是清掉全部 | 功能优化，采纳 |
| `fontWeight` | 新版用 `TypefaceStyle` 支持 100–900 字重，Recce 只有 bold 与 normal | 重要能力，需要支持 |
| `textDecorationLine` | 新版支持 `underline line-through` 组合值 | 重要能力，需要支持 |
| `cursorColor` | 采纳后会导致 Android 8.1 以下设备光标异常 | 不采纳 |
| `ellipsizeMode` / `textTransform` | 新版加了兜底默认值；Recce 写不存在的值上层直接编译报错 | 不采纳，保持现状 |
| `adjustsFontSizeToFit` | 改动量大，且 Recce 本来就没真正实现 | 暂时不采纳 |

注意后面几条不采纳的理由：都不是「做不了」，而是「采纳后比现在差」或「Recce 的编译期约束已经把它挡在前面了」。**对齐的目标是 RN 的语义，不是 RN 的实现细节**——这点两年材料里没被显式写出来，但所有判例都按这个口径判，值得补成一条原则。

**第三种做法：直接对源码。** 属性清单那条路是在文档层面做对照，2026 年多了一条更硬的路——差异扫描把 Recce 的 `android/recce/views` 与 RN 的 `ReactAndroid/.../views` 逐文件对读，只收高置信的行为差异，一次得到 14 条，4 条已修、10 条待修。它回答的是「做得对不对」，而属性矩阵只回答「有没有」：`snapToAlignment` 在属性表里是绿的（值收得到、三端都支持），但它在 `flingAndSnap` 里根本没参与计算，`pagingEnabled` 下 start / center / end 三种对齐全部退化成普通分页。这种问题盯着 RN 的属性文档看一辈子也发现不了。

![图 4：源码级差异扫描拿到 14 条高置信 bug，4 条已修、10 条待修](fig4-diff-scan.svg)

它还留了一条别处没写过的口径：第 10 条 `maxLength` 追加 `LengthFilter` 时数组下标写错、会抛 `ArrayIndexOutOfBoundsException`，作者注明「react-native-main 同位置仍能看到类似写法，因此这条不是 Recce 相对 RN main 的差异」，但仍建议顺手修。也就是说这类扫描只能识别「与对照物不同」，识别不了「两边都错」。

25 规划的最后一条目标是 Changelog 机制。背景写得很直白：Platform 层的实现对标的是 RN 0.63.x，而 RN 平均 2~3 个月发一个大版本，那两个已暴露的问题在 0.78.0 就修了、Recce 没跟，「实际上可能还有很多新版本中已经解决但我们未能察觉的潜在问题」。机制只审 Changelog 的 Fixed 部分，重点是 crash 相关的稳定性修复与组件样式渲染修复；节奏给了两套，选了简单那套（从 0.64.0 起每个迭代审 3 个大版本、约 6 个月追上），双线并行那套 5 个月能追上但被否，理由是「跟进压力较大、可能出现重复更新」。

### 2.3 布局引擎：Yoga 3.2.1，唯一跑完全程的一件

25 规划里动作最完整的一件，也是唯一把「调研 → 选型 → 方案 → 集成 → 分档放量 → 数据验收 → 回滚预案」跑完的。

选型先把四个候选（yoga / taffy / blink / stylo）的工程规模与 issue 数摊开，再逐项对照属性支持，结论是「核心属性支持程度 taffy 和 yoga 持平，属性支持的值 taffy 比 yoga 多」，但 taffy 当时不支持 `position: static` 与 RTL。三个方案里否掉「新增组件引入」（要过平台审批），选定「融合进 Recce 已有组件」，把「换成 Taffy」留作长期备选，原话是「这个事情可以等到布局计算迁移之后」。

落地上有几个细节值得记：三端各自引入 `release/3.2.1` 分支；Android 必须改包名（yoga 编译时用的包名是 `com.facebook.yoga`，`mrn:yoga` 也是，不改会冲突，改成 `com.meituan.android.recce.yoga`）；so 引入选「脚本拉仓库编译后取中间产物」而不是「把文件复制进工程」，理由是更新成本低、源码分离，代价是构建时间长；先保留 `mrn:yoga` 依赖做兜底；horn 开关默认 false，按 bundleName 白名单放量；双端所有埋点加通用字段 `use_new_yoga`。

上线载体选外卖商家端 7.16——C / Keeta 对稳定性与性能要求都高、不好做实验，所以找流量小的 B 端做验证。放量与观测结果见图 5。两个数字口径要留意：包体增量在两年里出现过两种说法（见待核实第 2 条）；benchmark 只在华为 Mate 30 上跑过，结论是「耗时上没有明显差距」，样本很薄，不能当性能结论用。

### 2.4 高级表现力：2026 新开的方向，P0 三项已落地

25 规划里这件事还不成方向，只是通用阴影从 0%（0/4）补到 100%（4/4），BoxShadow 挂在 1.32 排期上标「待完成」。26 规划把它单列为一条，理由是「全球化拉高 UI 水平」。

![图 6：2026 规划里高级表现力七项能力在 Recce、MRN、RN 三侧的支持情况](fig6-expressiveness.svg)

其中 SVG 的选型过程值得单独看：

| 方案 | 优点 | 缺点 | 结果 |
| --- | --- | --- | --- |
| RN-SVG | 三端一致性高，解析逻辑集中在 recce-ui | 总体开发成本高；子标签多时 native 视图多，性能存疑 | 未选 |
| androidsvg 纯原生 | 性能好（渲染出来是一个视图）；包体可控 | 三端一致性不是完全一致；维护成本较高 | **最终采用** |
| rust-resvg | 三端像素级一致；三端开发成本低 | 包体预估 +2.5MB；复杂 svg 下开销直线飙升 | 初选，后放弃 |
| rust 解析 + native 渲染 | — | 三端开发成本高；包体压力 | 未选 |
| thorvg | 三端像素级一致；性能高 | 三端开发成本较高；包体约 +600KB | 备选 |

benchmark 数据（Android）：复杂图 thorvg 52ms、native 70ms、rust >1000ms 且无法稳定加载；包体 native 最小 < thorvg 约 600KB < rust（优化 feature 后 Android release 增量 2.0MB，再去掉文本支持降到 1.0MB）。最终结论是从「像素级一致」退到了「性能与包体可控」。source 上有一条硬约束：只支持 utf8 与 base64 两种带前缀的字符串，不支持本地文件和远程图片；recce-ui 的宽高与其他样式都不作用到 svg 上。两条都是被业务实际用法顶出来的边界。

BoxShadow 的调研侧做得比较足：对齐 RN 0.83，把 Recce 的 elevation 方案、MRN 的 `shadow*` 方案、社区的 `@mrn/react-native-shadow-view`、Web CSS 的 `box-shadow` 摆在一起对照，兼容性写了 Android 9+（外阴影）/ 10+（内阴影）、iOS 13+，性能风险写了「低端 Android 设备上帧率可能从 60 FPS 下降到 15-20 FPS」。但「三、方案」的三端小节是空的。

### 2.5 背景与边框逻辑重构：三端一致性从口号变成了清单

26 侧真正的工程量在这里，但它在规划正文里没有独立条目，藏在子文档里。两个动因是「Recce 需要支持 BoxShadow」和「Recce 目前的背景渲染存在很多与 RN 不一致的问题，其中有开发梳理发现的，也有 QA 测试发现的」，一口气列了 14 条：

![图 7：背景与边框重构需求里 14 条已知三端不一致问题的分布](fig7-defect-map.svg)

清单里两类特别值得记：一是**同名不同义**，比如 `borderStyle` 在非图片场景下，Recce-Android 是「有圆角时视图被 border 挤、没圆角时 border 盖在视图上」，而 RN 不管有没有圆角都是盖在视图上；到了图片场景，Android / iOS 是 border 盖在图上、鸿蒙是视图被 border 挤，而 RN 是被挤。二是**属性互相干扰**，比如图片设了圆角时 `resizeMode` 失效。

结尾那句话是这两年材料里方法论价值最高的一句：

> 这些问题是已知的，当然还有很多未知的问题，如何主动识别并解决这些问题才是更重要的。

它和 26 规划关键结果里的「借助 AI 建立自动化测试，扩充测试用例，充分覆盖所有属性，提前发现潜在的不一致性问题」是同一件事的两面。到核实时，关键结果那一侧仍然只停在纸面上（用例从哪来、判定标准是什么都没写），但主动识别已经有一份样板做出来了，就是 2.2 里那份源码级差异扫描。

同一批工作还有个连带产物：为了支持 label 的 border 能力，iOS 侧把 `RECTextView` 的继承链从 `UIView` 改成 `RECView`，文字绘制交给新增的 `RECTextContentView`，并给出 15 条影响面清单（P0 四条：纯文字渲染、padding 生效、嵌套 Text、onClick 点击命中）。这类改动的影响面写法是这两年文档质量最高的一处。

### 2.6 版本维度：1.34 与 1.35 这两期在做什么

规划是按方向写的，实际落地是按版本排的，两套口径之间没有总表。把两期需求表并起来看：

| 版本 | 主要任务 | 与属性对齐的关系 |
| --- | --- | --- |
| 1.34 | touch 事件回调支持指针坐标（三端）、View 背景重构（Android 重构，iOS 与鸿蒙修 bug）、支持 BoxShadow（三端）、图片 source 属性重构、iOS 图片迁移 SD、差分包、样式热重载 | BoxShadow 与背景重构是「已支持属性对齐」的地基；Image 专表在这一期收口 |
| 1.35 | 触摸事件重构（P0）、Android 17 适配（P0）、Android yoga 加载方式优化（P0）、View 与 ScrollView 属性对齐（P1）、差异扫描（P2，暂停） | 属性对齐这一批集中在这一期，且被排在触摸事件重构之后 |

这张表也解释了一个读表时会困惑的点：**属性对齐在需求表里只是 P1**，P0 让给了触摸事件重构与平台适配。原因就在 2.1 里那 14 个 `onResponder*` 与 `hitSlop`、`pointerEvents` 一类属性——它们不是「没做」，是必须等触摸事件重构落地才能做。1.35 需求表的行序是有依赖依据的，只是这个依据没写在表里，得翻到专表才看得见。

## 五、放回上游坐标系里看

前面评的是这两年做得怎么样。这一章只做一件事：把文中几处关键选择放到上游/业界的现状里对齐，看有没有现成更省的路。出处为公开上游来源（2026-10-14 抓取）。

### 5.1 差异扫描这条路，业界有一个更便宜的形态

我们做的是「逐文件对读两个实现」。业界回答同一个问题（「我的实现和参照实现是否一致」）用的是**让参照实现自己产出期望值**：

| 做法 | 怎么落地 |
| --- | --- |
| 布局引擎自带的 fixture 对照（Yoga / taffy / stretch 都是这一套） | 用 HTML fixture 描述节点结构，在 Chrome 里渲染出**期望布局**，再拿本地实现跑同一组 fixture 比结果。Yoga 的 fixture 在 `gentest/fixtures`，`yarn gentest` 重新生成（[react/yoga](https://github.com/react/yoga)）。taffy 的 CONTRIBUTING 写明「Flexbox layouts are tested by validating that layouts written in this crate perform the same as in Chrome」，脚本会自动下载一对匹配的 Chrome for Testing 与 ChromeDriver；仓库里另有 `scripts/import-yoga-tests` 与 `scripts/diff-test-fixtures-with-yoga.sh`，**直接拿 Yoga 的用例做逐条差异对照**（[CONTRIBUTING](https://raw.githubusercontent.com/DioxusLabs/taffy/main/CONTRIBUTING.md)、[scripts](https://github.com/DioxusLabs/taffy/tree/main/scripts)） |
| 浏览器的 Web 测试 | 在 content_shell 里加载页面，把渲染输出或 JS 输出与已有 expected 文件比对（官方已把 LayoutTests 更名 Web Tests）；官方说明每次修 bug 都补一个 WPT（[Web Tests](https://chromium.googlesource.com/chromium/src/+/main/docs/testing/web_tests.md)） |
| Flutter 的 golden | `matchesGoldenFile` + `LocalFileComparator` 做**逐像素**比对，`flutter test --update-goldens` 刷基准；框架自身用 SkiaGold 把基准图放到集中服务。已知脆弱点官方自己写了：字体在不同平台/版本渲染不同，默认用 'Ahem' 方块字体，换 SDK 常要重出基准图（[goldenFileComparator](https://api.flutter.dev/flutter/flutter_test/goldenFileComparator.html)） |

对我们最直接的启发有两条。**第一条**：第四章第 3 条那个「属性 × 端 × 现状 × 期望」的表，在业界的可执行对应物是「期望值不由人写、由参照实现跑出来」。差异扫描那 14 条里，`snapToAlignment` 在 `flingAndSnap` 里没参与计算这种问题，恰好就是 fixture 对照能自动抓到的类型（输入相同、输出不同）。**第二条**：第四章第 4 条建议「不要一上来追像素级」，上游给了依据——Flutter 自己承认像素级 golden 会被字体差异污染，所以才默认换成方块字体。

### 5.3 一条会往回影响 2.1 的数字

Yoga 3.2（2024-12）才补上 `box-sizing` 与 `display: contents`；3.0 把 `PointScaleFactor` 从 root-only 改为 per-node，并移除了 `UseLegacyStretchBehaviour` 等一批 API；上游 RN 0.86（2026-06-11）的发布说明里仍列着 Yoga 布局回归修复（Android 绝对定位元素文本换行 #56651 等）。意思是：2.1 那张能力对照表按 3.2.1 与 RN 0.86 重算是对的，但引擎侧还会持续有回归修复进来，**跟版是常态动作，不是一次性收尾**（[Yoga 3.0](https://www.yogalayout.dev/blog/announcing-yoga-3.0)、[Yoga 3.2](https://www.yogalayout.dev/blog/announcing-yoga-3.2)、[RN 0.86](https://reactnative.dev/blog/2026/06/11/react-native-0.86)）。
