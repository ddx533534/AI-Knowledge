二、背景：起点很窄，但一件做不了的事顺带绑上两条诉求

补齐规划里，Recce 对标 RN 的属性支持度是：通用布局 93%（52/56，只缺 paddingHorizontal、gap、rowGap、columnGap）、ScrollView 44%（27/61）、Image 48%（24/50）、View 48%（46/94）、Label 46%（31/69）、Input 53%（41/67）、通用阴影 0%（0/4）。缺的 4 个里 gap 系列是 keeta 与前置组件近期要用的，定为 P0。

但补属性做不了：Recce 不实现布局计算，全部委托外部 Yoga，而这份 Yoga 是从 MRN 组件借来的，版本停在官方 1.18.0。补属性必须换引擎，换引擎顺带绑上两条诉求：

  • 隐性耦合：MRN 若升级 Yoga 而没周知 Recce 做测试，很可能造成线上问题，原文写「很大安全隐患」。
  • 已知 bug：1.18.0 上元素带 Position::Absolute 后 visible: false 失效（黑色块无法隐藏），1.18.0 及以下复现、3.2.1 正常。

五、下次怎么改

5.1 这次做对的

做对的 为什么它有效
问题重定义的层级 不写「补 4 个属性」写「依赖形态」，把上游的不确定性（MRN 随时可能升 Yoga）纳入设计目标，后面所有风险因此被提前处理，而不是等出事再补
双引擎共存即对照组 埋点带 use_new_yoga，不需要实验平台就能按人群对比；灰度单位是 uuid，与放量节奏天然对齐
不可逆动作后置 先并存、稳定后再解绑；发版走单拉特性分支而非合主分支。两处都把「回不去了」往后推，回滚边界干净
选小流量 B 端验证再谈合入 承认了 C 端不能做实验这个约束

补一句定性：这意味着整轮验证是「低风险验证」而非「统计验证」，这句话该写进结论，免得被后来的人当成 A/B 结论引用。

5.2 同类「换外部依赖」的升级，按这五条改

# 怎么做 这次的反例
1 把「为什么要升」逐条映射成验收项 升级理由有几条就该有几条对照，否则只验了「没变差」、没验「变好了」。这次 gap 是新增能力、absolute 隐藏是修 bug，两条都能测，都没进验收
2 异常率差异先做归因再下结论 判定「与本次变更无关」至少要有一处对照：按机型 / OS / bundle / 版本的新老分布对比，或把差异样本逐单追查。只比「异常类型集合」不够
3 指标差异先跟对照组自身的日间波动比 差异幅度小于对照组自身极差时，结论只能写「未见可归因差异」，不写方向性判断
4 上线前做一次真实回滚演练，并给出回滚生效时长 用本次已有的 use_new_yoga 埋点量出「下发 false 后该维度归零的耗时分布」，把回滚生效时间本身列为验收项
5 给「解除旧依赖」设一个带日期的退出条件 例如「全量后 N 周无 P1，且旧 Yoga 代码路径调用量归零」。缺了这条，双份 so 会一直留在包里

5.3 放量表要按样本量反推

上线记录 6.30 那行自己写着：「iOS App 当前灰度 1%（Android 看不到），叠加 Yoga 灰度 1% 基本没量了，这样收数据太慢了，也看不出问题，下午计划先放到 30%……Recce 指标个位级 PV，性能数据无法参考。」

叠加灰度必然稀释样本，这一步应该在设计放量表时就用目标指标的最小可检出差异反推，而不是先放量再看够不够。本次因为 Recce 指标只有个位级 PV，最终仍属低风险验证，「业务指标稳定」这句话的强度有限。

六、技术思路与业界方案

上面几章评的是「这件事做得怎么样」，这一章补两件前面没写的：1.18.0 到 3.2.1 之间引擎里到底变了什么（代码级），以及换布局引擎这件事上游是怎么做的。出处为公开上游来源（2026-10-14 抓取），可点开复核。

6.1 这五年引擎里变了什么

版本时间线：1.18.0 发布于 2019-11-08，此后官方 release 基本停滞（1.19.0 到 2021-05-21），2.0.0 是 2023-07-27，3.0.0 到 2024-03-05、3.1.0 到 2024-06、3.2.0 到 2024-12-02，最新 tag 仍是 v3.2.1（2024-12-13）；npm 包 yoga-layout 的 latest 同样停在 3.2.1。出处：tags、v3.2.1、npm registry。也就是说我们这次跟的不是「最新版本」，而是「引擎自 2024-12 起的稳定版」——它已经不是活跃开发中的分支了。

仓库形态：Yoga 没有归档，也没有并进 react-native 仓库，而是随 React 系整体从 facebook 组织迁到了 react 组织（RN 0.86 发布说明 记了这次组织迁移）；同时 RN 仓库内 vendor 了一份 Yoga 源码在 ReactCommon/yoga/，与 RN 一起发版。

3.0 的破坏性变更里，与本次升级直接相关的三条：支持 position: static，并把默认 position 由 static 改回 relative；移除 UseLegacyStretchBehaviour 相关 API；PointScaleFactor 由 root-only 改为 per-node。升级即解掉一批布局问题，物理基础就在这里（引擎重写了这些路径）。出处：Yoga 3.0 发布说明。

errata 机制 —— 升级同解一批问题、又可能引入新差异，是同一套机制的两面。 3.0 引入 AbsolutePositioningIncorrect、AbsolutePercentAgainstInnerSize 两个 erratum，3.2 干脆移除 legacy absolute positioning 代码路径、改用新 erratum AbsolutePositionWithoutInsetsExcludesPadding 保留兼容；官方明确说明 React Native 中默认开启旧行为。所以「跟版本」不是把版本号一改就完——每个 erratum 取哪个方向，本身就是一次有后果的选择，应当单独列出来当验收项。出处：3.0、3.2。

3.2 补上了两个会影响能力对照表的特性：box-sizing（且默认仍是 border-box，即使开 UseWebDefaults）与 display: contents。第二章那张「通用布局 93%、缺 gap 等 4 项」的对照表是按 3.2.1 之前的印象算的，补属性时值得按这一版重算一遍。

上游自己也没停下来：RN 0.86（2026-06-11）的发布说明里仍列着 Yoga 布局回归修复（Android 绝对定位元素文本换行 #56651、BoringLayout 负宽崩溃 #56007、display:contents 节点归属 #56422）。这说明「跟到 3.2.1 就稳定了」是个不成立的假设，跟版是常态动作。

API 层面要改的地方（若后续要自己编引擎）：YGFloatOptional 已改名 FloatOptional（#39196）；尺寸/长度不再用裸 float 表示，而是 StyleSizeLength / StyleLength（FloatOptional + Unit），Unit::Undefined 是合法状态，YGUndefined 就是 quiet_NaN()。出处：StyleSizeLength.h、YGValue.h。

顺带一条与 4.1 呼应的旁证：新版 so 比旧版小（348KB 对 409KB），而 3.2 移除 legacy absolute positioning 路径恰好是减代码的改动——方向一致，但不能据此断言因果。

6.2 替代引擎的现状（第三章选型表该按这个重算）

候选 现在是什么状态 与本次选型的出入

6.3 同一件事上游怎么做

环节 上游/业界现在的做法 与本次的差异 能不能借鉴
跟引擎大版本 RN 逐版跟 Yoga（0.74 跟 3.0、0.75 跟 3.1、0.77 跟 3.2），每次在发布说明里列行为变化与回归修复，并把 erratum 作为下游保留旧行为的开关 我们是「整包换」，没有逐 erratum 的决策与验收记录 值得。把 erratum 取值列成一张表写进验收项，成本很低
依赖形态（避免隐性耦合） vendor 进主仓、随框架发版 原先从 MRN 借，版本与升级节奏都由对方决定 本次做的自打包 + 改包名已经是同一方向，方向正确
新增能力的验收怎么定期望值 用 HTML fixture 描述节点结构、在 Chrome 里渲染出期望布局，再拿本地实现跑同一组 fixture 比对（Yoga 与 taffy 都这么做） 本次 gap 是新增能力，可测却没进验收项 值得。gap 这类纯布局能力的期望值可以直接生成，不必靠人工看图。详见《Recce-Host-布局逻辑迁移复盘》6.2
