## 二、背景：起点很窄，但一件做不了的事顺带绑上两条诉求

补齐规划里，Recce 对标 RN 的属性支持度是：通用布局 93%（52/56，只缺 `paddingHorizontal`、`gap`、`rowGap`、`columnGap`）、ScrollView 44%（27/61）、Image 48%（24/50）、View 48%（46/94）、Label 46%（31/69）、Input 53%（41/67）、通用阴影 0%（0/4）。缺的 4 个里 gap 系列是 keeta 与前置组件近期要用的，定为 P0。

但补属性做不了：Recce 不实现布局计算，全部委托外部 Yoga，而这份 Yoga 是从 MRN 组件借来的，版本停在官方 1.18.0。补属性必须换引擎，换引擎顺带绑上两条诉求：

- **隐性耦合**：MRN 若升级 Yoga 而没周知 Recce 做测试，很可能造成线上问题，原文写「很大安全隐患」。
- **已知 bug**：1.18.0 上元素带 `Position::Absolute` 后 `visible: false` 失效（黑色块无法隐藏），1.18.0 及以下复现、3.2.1 正常。

## 三、方案回顾

### 3.1 决策链

![图 1：五步单列决策链。第一步起点是补齐通用布局缺失属性；第二步发现做不到，因为 Recce 不实现布局计算、全部委托从 MRN 借来的 Yoga 1.18.0；第三步把问题重定义为依赖形态问题，一个动作同时绑上 gap 能力、MRN 静默升级的隐性耦合、absolute 元素 visible 失效三条诉求，这一格标红表示风险；第四步选型定为融合进已有组件，代价是两份 so 共存、包名必须改；第五步落地与验证，horn 按包名切双引擎、埋点带 use_new_yoga 形成对照，在外卖商家端按 uuid 阶梯放量。](fig1-decision-chain.svg)

### 3.2 选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Yoga 作为新增组件引入 | 未列 | 新增组件需要经过平台审批，引入成本较高 | 否 |
| Yoga 融合到 Recce 已有组件中 | 不需要新增组件，引入成本适中 | 未列 | **选中** |
| Yoga 替换为 Taffy | Benchmark 显示深树/超深树上更高效 | CSS 能力集不完善（不支持 RTL、不支持 `Position::Static`）；迁移成本高 | 长期备选 |

选型调研另有一张更细的四框架对照（Yoga / Taffy / Blink / Stylo），比的是工程规模（18W+ / 19W+ / 20W+ / 10W+ 行）、issue 数量（641 / 236 / 10000+ / 15）与近两年有 commit 的核心维护者数（18 / 29 / 88 / 27）。它支持了「Yoga 与 Taffy 在核心属性上持平、Taffy 属性值更多但缺 RTL 与 Static」，但最终决策落在引入成本上，不是技术能力上。

选「融合进已有组件」自带一个代价：**两份 Yoga so 必须共存**，而 `com.facebook.yoga` 与 `mrn:yoga` 的包名相同，编译时必须把包名改成 `com.meituan.android.recce.yoga`，产物重命名为 `recce-yoga.so`。

### 3.3 落地步骤

Android 是唯一写全的一端（主文档与规划下同名文档内容一致）：

1. 编译 Yoga 3.2.1 得 so，改包名、改名 `recce-yoga.so`。
2. so 引入取「方案一」：脚本拉 `recce-yoga` 仓库 → 取编译生成的未剥符号中间产物 so → 挪进 `recce-library` 的 jni 目录 → 删掉本地临时仓库。理由是更新成本低、源码不驻留项目目录；代价是每次构建要重新拉取编译。
3. jar 以 java 源码方式并入 `recce-library`，参考 `mrn:yoga` 里的 java 类。
4. 开关：horn 下发开关，默认 false。

iOS 与 harmony 在主文档里是空章节（只有标题）。上线记录补了包体：iOS 压缩前 +150.52KB、压缩后 +34KB；harmony 压缩前 +1047KB，因 harmony 无包体管控所以列为无风险。**三端各自的实现差异没有沉淀**，后续要单独改动时没有可参照的记录。

### 3.4 上线与放量

- 跟随 1.28 单拉特性分支 `feature/recce-89059528/yoga_3.2.1_integration` 发一个小版本，该版本相比 1.28 只多出 yoga 升级 + gap 支持，稳定后再合主分支。理由是「希望 Recce 具备 Gap 布局能力」与便于回滚。
- 验证 APP 选外卖商家端（7.16），诉求一栏写明原因是「C/Keeta 对稳定性和性能要求都很高，不太好做实验」。原计划的众包、骑手被划线删除，**没记录原因**。
- 按 uuid 阶梯放量：6.30 的 1% → 7.3 的 30% → 7.8 的 50% → 7.16 的 80% → 7.21 全量。
- 观测三类：Recce 内核性能与异常、支付订单转化率、业务客诉。

## 五、下次怎么改

### 5.1 这次做对的

| 做对的 | 为什么它有效 |
| --- | --- |
| 问题重定义的层级 | 不写「补 4 个属性」写「依赖形态」，把上游的不确定性（MRN 随时可能升 Yoga）纳入设计目标，后面所有风险因此被提前处理，而不是等出事再补 |
| 双引擎共存即对照组 | 埋点带 `use_new_yoga`，不需要实验平台就能按人群对比；灰度单位是 uuid，与放量节奏天然对齐 |
| 不可逆动作后置 | 先并存、稳定后再解绑；发版走单拉特性分支而非合主分支。两处都把「回不去了」往后推，回滚边界干净 |
| 选小流量 B 端验证再谈合入 | 承认了 C 端不能做实验这个约束 |

补一句定性：这意味着整轮验证是「低风险验证」而非「统计验证」，这句话该写进结论，免得被后来的人当成 A/B 结论引用。

### 5.2 同类「换外部依赖」的升级，按这五条改

| # | 怎么做 | 这次的反例 |
| --- | --- | --- |
| 1 | 把「为什么要升」逐条映射成验收项 | 升级理由有几条就该有几条对照，否则只验了「没变差」、没验「变好了」。这次 gap 是新增能力、absolute 隐藏是修 bug，两条都能测，都没进验收 |
| 2 | 异常率差异先做归因再下结论 | 判定「与本次变更无关」至少要有一处对照：按机型 / OS / bundle / 版本的新老分布对比，或把差异样本逐单追查。只比「异常类型集合」不够 |
| 3 | 指标差异先跟对照组自身的日间波动比 | 差异幅度小于对照组自身极差时，结论只能写「未见可归因差异」，不写方向性判断 |
| 4 | 上线前做一次真实回滚演练，并给出回滚生效时长 | 用本次已有的 `use_new_yoga` 埋点量出「下发 false 后该维度归零的耗时分布」，把回滚生效时间本身列为验收项 |
| 5 | 给「解除旧依赖」设一个带日期的退出条件 | 例如「全量后 N 周无 P1，且旧 Yoga 代码路径调用量归零」。缺了这条，双份 so 会一直留在包里 |

### 5.3 放量表要按样本量反推

上线记录 6.30 那行自己写着：「iOS App 当前灰度 1%（Android 看不到），叠加 Yoga 灰度 1% 基本没量了，这样收数据太慢了，也看不出问题，下午计划先放到 30%……Recce 指标个位级 PV，性能数据无法参考。」

叠加灰度必然稀释样本，这一步应该在设计放量表时就用目标指标的最小可检出差异反推，而不是先放量再看够不够。本次因为 Recce 指标只有个位级 PV，最终仍属低风险验证，「业务指标稳定」这句话的强度有限。

## 六、技术思路与业界方案

上面几章评的是「这件事做得怎么样」，这一章补两件前面没写的：1.18.0 到 3.2.1 之间引擎里到底变了什么（代码级），以及换布局引擎这件事上游是怎么做的。出处为公开上游来源（2026-10-14 抓取），可点开复核。

### 6.1 这五年引擎里变了什么

**版本时间线**：1.18.0 发布于 2019-11-08，此后官方 release 基本停滞（1.19.0 到 2021-05-21），2.0.0 是 2023-07-27，3.0.0 到 2024-03-05、3.1.0 到 2024-06、3.2.0 到 2024-12-02，**最新 tag 仍是 v3.2.1（2024-12-13）**；npm 包 `yoga-layout` 的 latest 同样停在 3.2.1。出处：[tags](https://github.com/react/yoga/tags)、[v3.2.1](https://github.com/react/yoga/releases/tag/v3.2.1)、[npm registry](https://registry.npmjs.org/-/v1/search?text=yoga-layout)。也就是说我们这次跟的不是「最新版本」，而是「引擎自 2024-12 起的稳定版」——它已经不是活跃开发中的分支了。

**仓库形态**：Yoga 没有归档，也没有并进 react-native 仓库，而是随 React 系整体从 `facebook` 组织迁到了 `react` 组织（[RN 0.86 发布说明](https://reactnative.dev/blog/2026/06/11/react-native-0.86) 记了这次组织迁移）；同时 RN 仓库内 vendor 了一份 Yoga 源码在 `ReactCommon/yoga/`，**与 RN 一起发版**。

**3.0 的破坏性变更**里，与本次升级直接相关的三条：支持 `position: static`，并把默认 position 由 static 改回 `relative`；移除 `UseLegacyStretchBehaviour` 相关 API；**`PointScaleFactor` 由 root-only 改为 per-node**。升级即解掉一批布局问题，物理基础就在这里（引擎重写了这些路径）。出处：[Yoga 3.0 发布说明](https://www.yogalayout.dev/blog/announcing-yoga-3.0)。

**errata 机制 —— 升级同解一批问题、又可能引入新差异，是同一套机制的两面。** 3.0 引入 `AbsolutePositioningIncorrect`、`AbsolutePercentAgainstInnerSize` 两个 erratum，3.2 干脆**移除 legacy absolute positioning 代码路径**、改用新 erratum `AbsolutePositionWithoutInsetsExcludesPadding` 保留兼容；官方明确说明 React Native 中默认开启旧行为。所以「跟版本」不是把版本号一改就完——每个 erratum 取哪个方向，本身就是一次有后果的选择，应当单独列出来当验收项。出处：[3.0](https://www.yogalayout.dev/blog/announcing-yoga-3.0)、[3.2](https://www.yogalayout.dev/blog/announcing-yoga-3.2)。

**3.2 补上了两个会影响能力对照表的特性**：`box-sizing`（且默认仍是 border-box，即使开 `UseWebDefaults`）与 `display: contents`。第二章那张「通用布局 93%、缺 gap 等 4 项」的对照表是按 3.2.1 之前的印象算的，补属性时值得按这一版重算一遍。

**上游自己也没停下来**：RN 0.86（2026-06-11）的发布说明里仍列着 Yoga 布局回归修复（Android 绝对定位元素文本换行 #56651、BoringLayout 负宽崩溃 #56007、display:contents 节点归属 #56422）。这说明「跟到 3.2.1 就稳定了」是个不成立的假设，跟版是常态动作。

**API 层面要改的地方**（若后续要自己编引擎）：`YGFloatOptional` 已改名 `FloatOptional`（[#39196](https://github.com/facebook/react-native/issues/39196)）；尺寸/长度不再用裸 float 表示，而是 `StyleSizeLength` / `StyleLength`（`FloatOptional` + `Unit`），`Unit::Undefined` 是合法状态，`YGUndefined` 就是 `quiet_NaN()`。出处：[StyleSizeLength.h](https://raw.githubusercontent.com/facebook/react-native/main/packages/react-native/ReactCommon/yoga/yoga/style/StyleSizeLength.h)、[YGValue.h](https://raw.githubusercontent.com/facebook/react-native/main/packages/react-native/ReactCommon/yoga/yoga/YGValue.h)。

顺带一条与 4.1 呼应的旁证：新版 so 比旧版小（348KB 对 409KB），而 3.2 移除 legacy absolute positioning 路径恰好是减代码的改动——方向一致，但不能据此断言因果。

### 6.2 替代引擎的现状（第三章选型表该按这个重算）

### 6.3 同一件事上游怎么做

| 环节 | 上游/业界现在的做法 | 与本次的差异 | 能不能借鉴 |
| --- | --- | --- | --- |
| 跟引擎大版本 | RN 逐版跟 Yoga（0.74 跟 3.0、0.75 跟 3.1、0.77 跟 3.2），每次在发布说明里列行为变化与回归修复，并把 erratum 作为下游保留旧行为的开关 | 我们是「整包换」，没有逐 erratum 的决策与验收记录 | 值得。把 erratum 取值列成一张表写进验收项，成本很低 |
| 依赖形态（避免隐性耦合） | vendor 进主仓、随框架发版 | 原先从 MRN 借，版本与升级节奏都由对方决定 | 本次做的自打包 + 改包名已经是同一方向，方向正确 |
| 新增能力的验收怎么定期望值 | 用 HTML fixture 描述节点结构、在 Chrome 里渲染出期望布局，再拿本地实现跑同一组 fixture 比对（Yoga 与 taffy 都这么做） | 本次 gap 是新增能力，可测却没进验收项 | 值得。gap 这类纯布局能力的期望值可以直接生成，不必靠人工看图。详见《Recce-Host-布局逻辑迁移复盘》6.2 |
