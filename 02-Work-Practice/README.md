# 02-Work-Practice — 工作实践

## 用途

记录工作技术实践、个人学习与算法训练复盘，以及非日报技术专题。每份文档说明对象、实际过程、证据、修正与未决问题。

2026-10-17 用户明确要求：今天全部学习与算法内容整理到实践目录，Daily 中非日报内容一并移入。工作实践、学习训练、外部专题应标明各自来源，不能互相冒充实测。

与知识库其它目录的关系：

- 本目录是**实践记录**，不是归档原文。原始材料（学城文档、源码、上游 README）仍在各自源头，这里写的是对照后的结论。
- 从实践里抽出的、可脱离具体场景复用的技术结论，按 `AGENTS.md` 的整理约定提炼到 `01-Knowledge`；提炼时只用能公开复核的材料当来源，不把只有内网能打开的材料当唯一证据。
- 实践文档本身**不自动**成为知识节点。
- 与 `03-Daily` 的分工：Daily 只保留每日行业简报；独立专题、译文与个人训练复盘均放本目录。

## 文件约定

| 约定 | 说明 |
| --- | --- |
| 文件名 | 用「对象 A 与对象 B 的对照」「X 方案实践」这类能一眼看出问题的写法，工作方案通常不用日期前缀；迁入专题与逐日训练可保留日期前缀，便于保留来源与旧链接 |
| 核实日期 | 正文开头写这一份是哪天核实的，材料版本一起写清 |
| 版本口径 | 参与对照的每一方都要写清版本/日期；版本不齐时显式说明，不假装同条件 |
| 数据来源 | 上游源码以 GitHub 原始文件直读为准；内网文档用《文档名》指代、不写学城 contentId（ID 记在 `.workbuddy/memory` 便于回溯），写清读取日期；厂商自测数据标注出处，不写成既成事实 |
| 行文体例 | 有对照、有复盘的成分就用表格：判断、证据、动作分列，一份方案一行，避免成段叙述；表格里已经写过的内容，正文不复述，只写读法和限制。同一份文档里的判断与动作不要在两节重复各写一遍 |
| 未决问题 | 收尾单列一节，写清缺什么数据、哪一处还没核实 |

## 配图

对照类文档要把调用链、时序、判定逻辑画出来，不要通篇文字。

- 图号按正文出现的先后连排，`figN` 的文件名跟着走。中途往前面插一节，要连带重排图号、文件名和图注里的编号。
- 引用写法 `![图 N：说明](assets/<日期>/figN-短名.svg)`。**alt 就是图注**，要能独立看懂，不依赖上下文；图里的数字与正文一致。
- 只画正文已经写了的事实，不引入新结论。样式跟着日报走：浅色、扁平、细边框，不用渐变、阴影、emoji、外链字体。
- 颜色只用来表达含义，不装饰。本目录约定的口径是蓝＝RN 官方、橙＝自研（Recce）与事件触发式、绿＝可用或推荐、红＝不可用、灰＝中性说明或原文未写。
- 生成 HTML 时把 SVG 内联、位图转 base64，成品保持单文件、无外部依赖。

## 内容结构

不强制套模板，但通常包含这几块：

1. **结论先行**：复盘类开头先给一条判断（例如「这几份版本下来最大的启发是什么」），先回答它再进材料。
2. **背景与问题**：在什么场景下遇到的，为什么它是个问题。
3. **参与对照的方案**：各自的实现原理，按调用链讲清在哪一层做事。
4. **逐维度对照**：用表格，维度要能对上，对不上的维度单独说明。
5. **结论核对**：原方案里的判断哪些成立、哪些要修正，给条件。
6. **分场景建议**：落到「什么情况选哪个」，不止给一个总排序；这一节只放动作与证据，不复述开头的判断。
7. **待核实**：缺的实测数据、没读透的原文、需要按最新版本复核的结论。

术语多的文档在正文前面补一张词表，先给白话解释再展开，读者不用回头查。
