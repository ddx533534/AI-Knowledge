一、结论：这八份版本下来，最大的启发是什么

一句话：1.28 到 1.35 做的主要不是「加功能」，而是「把借来的东西收回来」。 顺着这句有五条判断，对应的动作放在第四节。

# 判断 证据
1 对标的锚点从 MRN 换成 RN，方案性质就从「补能力」变成「消差异」 1.28–1.31 的参照物还是 MRN（「MPN 已经有了」「和 MRN 对齐」）；1.32 之后几乎每份第一句都变成「对齐 RN」，验收从「业务能用」变成「和 RN 逐字段一致」——这是被动接需求转向主动定标准的分界点
2 凡是「多端不一致」，最后都是把差异收口到一处，不是三端各修一遍 正面：背景收口到 CompositeBackgroundDrawable、触摸收口到 RecceTouchTargetHelper、属性协议收口到 pdef 生成。反面：Lottie 的 /dist/lottie 路径、SVG 的 data: 前缀、字体加载的 bundle 内字体，三份方案各定义一套「资源从哪来」——同一个抽象缺失被付了三次成本
3 选型的分水岭永远是宿主 App 的包体余量，不是技术优劣 点评当时的 Android 余量约 1.09MB，候选方案增量在 194KB 到 2.5MB 之间；Yoga 自打包 so、SVG 从 resvg 退回原生、thorvg 因 +600KB 落选，三次都倒在这条线上
4 重构类方案的收益大头是「清历史债」，立项理由却只写「加能力」 图片重构顺带修掉 ResizeMode 一串问题与继承链的重复实现；背景重构一次收口 14 条三端不一致；触摸新架构顺手解锁一批依赖它的点击属性
5 最弱的一环不是技术判断，是证据强度 18 份里能在文档内给出可复核数字的只有 5 份（Yoga 引入的耗时对照、Android 升 yoga 的包体明细、SVG 的耗时与包体、字体加载的缓存耗时、Android 17 适配的 DAU 口径）；多数「风险」章节是 todo 或「待定」，Benchmark 多为单机单次、无对照

二、全景

类别 方案 共同点
换依赖（3） Yoga 引入、Android 升 yoga、鸿蒙升 yoga 借来的引擎要收回自己手里；代价是包体与双引擎共存
新增能力（5） Lottie、SVG、字体加载、文本渐变、Touch 指针 每个能力都要先定「资源从哪来、数据长什么样」
重构（3） 图片重构、背景重构、触摸新架构 立项理由写「加能力」，实际收益大头是「清历史债」
对齐与适配（4） 字体路径、Image 二期、Android 17、补属性 判据从「代码里有」换成「线上有流量」
机制与扫描（3） 实名调研、差异扫描、安全区域 交的是机制或边界判断，不是功能，验收标准与功能型方案不同

三、逐方案复盘

按类别排成五张表。每行四个内容列分别是：要解决的问题 → 做法与当时的取舍 → 2026 年视角下更优的解法 → 可带走的启发。

3.1 换依赖（3 份）

方案（版本） 问题 做法与取舍 2026 视角：更优解 可带走的启发
Yoga 引入（1.28） 布局计算全靠从 MRN 借的 Yoga，版本停在官方 1.18.0。三条诉求撞在一起：业务要 gap、上游若静默升级无人知会、1.18.0 有 absolute 元素 visible: false 失效的 bug 开源 3.2.1 源码入 recce-library、改包名、自编 recce-yoga.so 与 mrn:yoga 共存；horn 开关 use_new_yoga 默认关，特性分支先发特性版验证。公司不允许直接依赖开源组件，只能自建；代价是包体（两份文档 428KB 与 489.52KB 两个口径）、双 so 共存、开关用静态变量「只有重启 APP 生效」 ① 版本判断仍成立：Yoga 最新发布版到 2026-10 还是 3.2.1，「等上游发新版」当时就不是选项。② 开关应走 Recce 已有的按 bundleName 白名单，「只有重启生效」把可回滚缩水了。③ 真正的缺口是「引擎怎么跟上游」的升级机制，换 Taffy 不是答案（仍缺 RTL 与 Position::Static） 把「补一个属性」重定义成「换掉一个依赖」，一次拿到功能、稳定性、历史 bug 三份收益；代价是验收面变宽，必须配共存 + 开关 + 对照埋点。成色看开关的生效粒度
Android 升 yoga（1.31） 三端统一升级里 Android 侧的落地记录 两方案对比后选「导源码改包名自建」；so 构建放 ndk_build.gradle、产物进 library 的 jni，加载走 Soloader 且时机不变；用 readelf 查出新 so 不再依赖 libc++_shared 与 libfd。风险里写包体：Android 压缩前 +489.52KB、压缩后 +194KB ① readelf 查依赖并裁掉多余 so 是最值钱的动作，该固化成引入原生库的标准步骤。② so 加载时机是复制来的不是设计出来的，应收口成注册表（每个 so 声明依赖与时机、统一排序）。③ 同版本两份文档包体口径分叉（428 与 489.52KB），说明数据没有唯一出处 引入第三方原生库，验收项里必须有「so 依赖链」；同一个数字在文档间不一致，问题不在数字，在没有唯一出处
鸿蒙升 yoga（1.31） 同一次升级的鸿蒙侧落地 yoga-rs 升 0.5.3、同步 Yoga 3.2.1 改动；Config 加 YGErrata 兼容旧行为；wasai 侧换 get_node_ref_context 以支持 gap。风险里写明「直接升级、并无 AB，需要重点关注」 ① 同一次升级，Android 是「双引擎 + 开关」、鸿蒙是「无 AB」，两套纪律；不能共存也要定义回滚路径与生效条件。② 拿到 YGErrata 却没用（文档写「鸿蒙布局架构没有用到」）——不能 AB 的端最该用它当安全网。③ 风险止步于「需要重点关注」，该翻成必测清单、回滚顺序、决策人 上游给了兼容开关就等于拿到了安全网，不用它等于把确定性还回去；平台放量能力越弱越要靠上游开关兜底

3.2 新增能力（5 份）

方案（版本） 问题 做法与取舍 2026 视角：更优解 可带走的启发
Lottie（1.29） keeta 反馈竞品 talabat 动画表现好、Recce 动画能力有限；外卖在优化首页到提单链路，动画需求会持续增加 新增 recce-lottie module（按需集成、要走新增 module 审批），参考 lottie-react-native 与公司内 MRN；约定动画 json 必须放 bundle 根 dist/lottie 下、用 DioBundleUtil 拼路径。属性支持 8 项、不支持 4 项，其中 3 项有理由，AutoPlay 标了未支持却没写理由 ① 硬编码 /dist/lottie 是可以避免的耦合，1.29 就该抽出「Recce 资源解析」一层（bundle／data URI／远端各一来源），后面 SVG 的前缀规则、bundle 内字体都是同一层能力被各写一遍。② 「表里列了却不做」的项必须写理由，否则后来者分不出有意不做和漏了。③ Lottie 与 SVG 本可共用引擎（thorvg 两者都支持），两个决策分开做就看不到交集 相近窗口内的一批新能力，先看能不能共用一层（引擎／资源解析／属性协议）再逐个决策；按需求逐个立项最容易重复造轮子
SVG（1.32） 业务需要 SVG 能力 五方案对比（RN-SVG／androidsvg／rust-resvg／rust 解析 + native 渲染／thorvg）后初选 resvg、最终改原生；source 只支持 data:image/svg+xml;utf8, 与 ;base64, 两种前缀。取舍全在包体与耗时：resvg 带文本 +2.0MB、去文本 1MB，thorvg +600KB，原生最小；复杂图耗时 thorvg 52ms、native 70ms、resvg >1000ms 且无法稳定加载 ① 回退原生的结论仍成立，但理由该换：thorvg 的 Rust 绑定已到 0.5.1（2026-08）却自述「尚未可用于生产」，说明「像素级一致」这条路两年后仍未成熟。② 真正的缺口是共同契约：没写下「支持的标签／属性白名单 + 逐项三端用例」，「三端不一致」这个被否掉的风险原样保留，只是变成长期维护风险。③ SVG 该走与其它图片相同的 source 解析链，只在拿到字节后分流解码器 「像素级一致」和「包体」在移动端常不可兼得，判据是宿主包体余量不是技术优劣；选完要留一条「回头看」——否掉的那条路现在成熟了没有
字体加载（1.33） 微贷要三类能力：iconfont、bundle 内字体（业务把字体放进 bundle）、远端 URL 字体 远端 URL 判「无需支持」，聚焦 bundle 内字体，来源用 FontFamily::new("bundle-xxx.ttf") 显式标识。缓存用实测论证：无缓存每次约 10ms、x 个 label 约 10x ms，加缓存后首次约 4ms、之后 0ms；key 选全路径，否掉字体名（下发新版后仍用旧字体、跨业务冲突）与 md5（多一次 IO）；LRU 限数量防 OOM ① 这是 18 份里实测支撑做得最好的一份，10／4／0ms 三个数字可直接当书写模板。② 缓存 key 还有第三档没展开：内容指纹放构建期算（构建时把 md5 写进清单，运行期零 IO）或运行期「路径 + 文件长度 + 首尾若干字节」弱指纹。③ 跨 bundle 共享的运行期限制可以在构建期做资源去重解决。④ 远端「无需支持」安全上合理，但该把理由写出来 缓存 key 只要记一条——必须能区分版本；真正的最优解常在构建期不在运行期；运行期做不到的事先想能不能挪到构建期
文本渐变（1.33） 微贷要文本渐变，Recce 不支持 两方案对比后倾向 MaskedView（通用性强、渐变内容可以是任意 View／Drawable，但需离屏 layer 与 bitmap、低版本合成坑多）；TextPaint Shader 更快更简单但只能用于文本。给出 RN RNCMaskedView 的 DST_IN 实现与 recce-ui 包装方式。踩坑：RecceMaskedView 只在 child == getChildAt(0) 时标脏 mask，小米成立、华为 Mate30 不成立（回调的是更深的 RecceTextView），表现为「子文本变了但 mask 没刷新」 ① 标脏条件应从「是不是第 0 个 child」改成「是不是 mask 视图的后代」，就与层级数无关、不会换机型失效——搬开源实现第一件事是列出它依赖的平台假设（第几个 child、回调里是谁、依赖几层）。② 「通用性强」在只有一类实际用途时是负收益：业务诉求就是文字颜色渐变，Shader 十行以内、无离屏合成。③ 要通用就该反过来先让提出方给出第二个用例，有排期才叫通用 搬开源实现时把平台假设换成结构性判断（是不是后代），不要换成机型名单；通用性只有在有第二个用例排期时才是收益
Touch 指针（1.34） 四个 touch 事件 prop 回调不携带任何事件数据（OnTouchStart 的 Response 是 ()、OnTouchMove 是裸 String），微贷做不了拖拽、自定义手势、点击涟漪、画板 定义 TouchPoint（location／page／screen 三组坐标 + identifier、timestamp、force）与 TouchEventData（touches／changedTouches），命名对齐 RN 的 nativeEvent；Rust 侧用强类型替代裸 String、反序列化失败走 Default 不 panic；MVP 不支持多指；MotionEvent 在回调里同步提取不持有引用；验收 8 条（含中点点击 location_x ≈ 100、误差 ≤ 2dp、timestamp 单调递增、三端一致） ① 这是 18 份里「字段规格 + 边界条件 + 验收标准」三样都齐的唯一一份，可直接当协议类方案的模板。② 协议形态埋了返工点：定成数组但 MVP 只有一个元素，应按「以后一定有」的形态定死、只在「填几个」上做减法。③ timestamp 用相对系统启动的单调时间而非墙上时钟是对的，可作为同类字段的默认约定 协议类改动按「以后一定有」的形态定结构，MVP 只减数量不减结构；边界条件表（会被 recycle、压感可能不支持、反序列化可能失败）比字段表更值钱

3.3 重构（3 份）

方案（版本） 问题 做法与取舍 2026 视角：更优解 可带走的启发
图片重构（1.31） ResizeMode 设 Stretch 与动态更新都无效、fit_start／fit_end 未支持。根因两层：RecceRoundImageView 把普通图误判为动画图、又用原始尺寸覆盖了一遍绘制边界；MTRecceRoundImageView 子类大量无脑调 super，而 super 操作的是父类成员 认定根因是「父子关系错误」，解除父子关系、抽公共基类（美团与开源实现各自一套），设 ResizeMode 时把图片状态置 Dirty；fit_start／fit_end 与 iOS 沟通后挪到 1.32。抽基类仍保留继承，只是把「父子」换成「兄弟」 ① 更彻底的是改组合：外层包一个持有 ImageView + 一组 Drawable 的组合对象（1.34 背景重构最后就是这个形态），抽基类只解决「谁调谁」，没解决「子类覆盖父类时静默失效」。② configureBounds 的坑是「在别人的决策点上二次覆盖」，不该覆盖系统已算好的边界。③ 它与 1.35 的差异扫描是同一问题的两半，却没有互相引用 「本地版继承开源版」一旦上游改了内部实现，子类的 super 会静默失效，标志是子类里出现大量 super；修它要把父子关系一起拆掉，只加 override 治不好
背景重构（1.34） 三端背景渲染不一致的问题越来越多（UIAutomation 发现）；生活费、月付与收银台要类 RN BoxShadow 的高级阴影；将来的背景图与轮廓线在现有架构上支持成本很高 全部背景收口到 CompositeBackgroundDrawable（内部管背景／边框／内外阴影三个 Drawable），对齐 RN 的 BackgroundStyleApplicator 形态，ViewManager 只 set 一个组合 Drawable。手法：背景色用 StateListDrawable 持正常与按下态；borderStyle 与四边不统一的冲突用 clipPath 裁梯形；内阴影 Android 10+、外阴影 9+；elevation 重写 getOutline 让投影跟圆角。测试：三端各一台 + 用 RN 写同一套用例跑第四台 ① 抄上游抄的是「职责划分」不是代码，且有一处比上游好：用观察者模式让 Drawable 自刷新，RN 是逐个手动 invalidate——这种「抄得比上游好」的点该显式写出来。② 两处「技术已具备却判暂不实现」可以再收：单边 borderStyle 用的就是同一个 clipPath 手法，边际成本只剩增量。③ 「RN 对照组」最该固化成流程——三端一致只能说明三端内部一致，与 RN 同机对照才能说明「和标准一致」 照上游抄要抄职责划分不抄代码，发现上游更笨就用更好的写法并写下来；把上游跑成对照组，比「三端各测一遍」高一个证据等级
触摸新架构（1.35） 旧架构依托 Android 原生分发（找最深的 View、向上冒泡到第一个设了 handler 的 View 返回 true），三条缺点：对原生有侵入（ScrollView 设 OnTouchListener 后返回 true 会阻碍滚动）、移出父布局范围的 View 点击不触发、热区只能在父 View 上设 TouchDelegate 改成 RN 形态：RecceRootView 统一观察 touch 流、ACTION_DOWN 锁定整段手势的 target，RecceTouchTargetHelper 从 root 递归 DFS（更深更靠上优先），pointerEvents 四种取值决定命中，边界考虑 hitSlop／overflow／clipChildren／transform（逆矩阵映射局部坐标）；native 只发 touch 流，click 与 longclick 交给 recce-ui。另补两处 RN 没专门管的：move 按帧回调（Choreographer.postFrameCallback）与双发去重。共存选「加开关不新增属性、由 recce-ui 统一向业务发事件」 ① 这是技术含量最高的一份，形态也对：不是抄 RN 的代码，而是在 Recce 里重实现 RN 的命中算法并补上 RN 没管的两处。② 接管成本没列全：多指与无障碍被列为 P0 未做，而这恰是「绕开原生」的必然代价，应显式列出接管清单（多指、无障碍、焦点、TV 遥控方向键）。③ move 按帧节流改变了事件语义（次数不再等于真实移动次数），应给「是否逐条收取」的开关。④ 共存方案选得对：差异收在 native 与 recce-ui 之间、不给业务加心智负担 原生能力与上层期望冲突时「绕开原生自己做一套」是对的，但要一并接管原生的隐式收益（无障碍、多指、焦点）；接管清单不写全，下一轮就会以缺陷的形式补回来

3.4 对齐与适配（4 份）

字体路径（1.30） keeta 把字体文件目录从 assets 挪到 res，fontFamily 失效；短期让 keeta 在 assets 再放一套字体不解决根因 三个方案（容器传「字体路径 + 名称到资源的映射」／「组装好的排列组合到 Typeface 的 map」／「字体文件到 FontFamily 的 map」）推荐第三个；随后 keeta 把文件名从大写改成小写，参数传递方案又改推第一个。多字体匹配只支持 Android 10 及以上。三个方案的差别其实是「谁负责把业务的字体标识解析成 Typeface」 ① 分歧点本可以消掉：先定 FontResolver 接口（res／font、assets、bundle 内、远端各一实现）再定数据形状，「从哪个目录取」「文件名大小写」就只是实现内部的细节——这也是方案选完紧接着又得再选一次的原因；1.33 字体加载实际做到了，只是晚了三个版本。② 用「多加一层映射」掩盖「命名不统一」是把问题往后推，命名该在约定层解决（命名规范 + 打包期校验） 备选方案的分歧点是「复杂度放哪一层」时，先定接口再定数据形状；一个方案选完不久又在同一组选项里再选一次，基本可判定接口没抽出来
Image 二期（1.32） 远程图被服务端判为非法源、需要在请求里补 headers；三端图片属性与 MRN 不对齐；QA 报的图片缺陷（背景边框类归到 1.34 背景重构） 新增 capInsets、fadeDuration、headers、onLoadStart，resizeMode 值域做对齐；同时修一批差异：Android 用 state 作 source 会多触发一次 error、source 置空串时不响应、capInsets 越界产生灰区（改为直接失效）、Picasso 重绘前先把 drawable 置空导致闪白（保存上一张图 + 启用内存缓存） ① 这批修复有同一个结构——状态机边界没覆盖全（没设过就报错、置空不响应、重绘前先清空、越界不校验），更优是一开始把 source／style／回调三者的状态机画出来统一实现。② Picasso 那条是「绕过库的语义缺失」，更优是用支持 placeholder／error 语义的加载器。③ capInsets 的降级规则对外可见，该写进接口约定而不是只写在实现里 同一批 bug 反复落在「状态机边界」上，说明缺的是状态机不是补丁；「某条件下不触发／多触发一次」这类缺陷连着来，就该停手先画状态机
Android 17 适配（1.35） Android 17 于 2026-06-16 发布，收紧了隐私安全、后台行为与开发规范；美团 App 安卓 17 设备 DAU 约 8000（7 月 1 日） 梳理被删 API：StaticLayout 旧版多参构造（影响 RecceSwitchButton、RecceTextShadowNode）、TextView.mCursorDrawableRes 反射被删（影响 RecceTextInputManager）。逐项判：label 与 input 早已适配（API 23+ 走 StaticLayout.Builder）无需改；SwitchButton 需修，但线上没有业务使用，跟美团主版本即可 ① 「线上没有业务在用」是关键判据，该显式固化成规则：适配看线上流量，不看代码引用。② 反射 API 被删是确定趋势，该一次改掉而不是加版本判断——换成语义等价的公开途径（主题属性 android:textCursorDrawable）或自绘光标。③ 更彻底的是出「删除清单」而不是「适配清单」：无流量的组件从 SDK 摘出去，适配成本直接归零 系统版本适配的第一问不是「怎么改」，而是「这段代码线上还有没有流量」；没流量的引用不该进适配清单，该进删除清单
补属性（1.35） ScrollView 缺 maintainVisibleContentPosition、scrollsChildToFocus；View 缺 removeClippedSubviews、needsOffscreenAlphaCompositing、一组 nextFocus*、focusable／tabIndex、hitSlop、pointerEvents 等 分两类。真补行为：maintainVisibleContentPosition（属性设了才懒创建 helper、布局变化记首个可见锚点、内容插入后按锚点反向调 offset、接近顶部自动回顶）、scrollsChildToFocus、removeClippedSubviews。只补协议：focusable／tabIndex／hitSlop／pointerEvents／renderToHardwareTextureAndroid 只补定义与读写入口、预留实现点。分界本质是「行为依赖别的工作」（hitSlop／pointerEvents 依赖触摸重构，这正是需求把触摸重构列 P0、属性对齐列 P1 的原因） ① 「先补协议、后补行为」手法本身对，危险在可观测性：属性收下却不生效，业务会以为已经支持，该给可观测标记（显式标 no-op、或首次下发打一次性日志）。② 依赖关系要反过来驱动排期，否则会先交付一批注定返工的 no-op。③ removeClippedSubviews 从 ScrollView 专属上移为 View 通用、导入路径变了，这类变更要单独列一节「升级需知」 「补齐属性」真正的危险不是漏做，而是属性收下了但不生效；补协议与补行为要显式分开标注，行为依赖另一项架构改动时必须同批排期

方案（版本） 问题 做法与取舍 2026 视角：更优解 可带走的启发
实名调研（1.35） 实名认证业务要在 Recce 里做相册网格、图片预览、裁剪等对性能和系统能力要求高的区域 把「自定义业务 Native View」做成一项能力交付：业务自建组件仓库，走 pdef 声明（组件名、属性、事件、版本 feature）→ generate.sh 生成 native 与 Rust 产物 → 实现 View／ViewManager／ShadowNode／Plugin → 业务依赖并在 rsx! 里使用。同时划边界：文案、资源位、弹窗、实验策略留 Recce；相册网格、预览、裁剪、复杂手势、高性能列表做 Native View；权限、拍照、上传、OCR、路由、埋点走 Bridge。风险列了协议稳定性、别把业务流程写死、图片不走 Base64、Native View 名需预置、组件包与 crate 版本配套 ① 这是「能力交付型」方案，验收标准该不同：功能型看「功能对不对」，机制型看「没参与过的人能不能照着独立接入一次」。文档只有步骤与一个示例仓库链接，缺最小可跑样例 + 生成脚本校验（CI 里跑 generate.sh 比对产物），而后者才是机制型交付的成立条件。② 「客户端低版本没集成、业务自行版控」最容易出事故，该让 Recce 对未注册组件给可观测降级（占位视图 + 上报）。③ pdef 作为唯一协议源头是最值钱的设计，可反过来推广到内部组件——新能力优先走 pdef，不手写三端属性 能力交付型（交机制）与功能交付型（交特性）要分开写；机制型的验收标准是「外部团队能独立接入一次」，产出必须含可运行样例与生成校验，光有步骤说明不算交付
差异扫描（1.35） Recce 的 Android 组件是从 RN 抄来改造的，长期分叉后不知道差在哪 Recce 的 views 目录与 RN 的 views 目录逐文件对读，只记高置信的 bug 或行为差异（未支持属性、无 RN core 对照的不纳入），得 14 条（ScrollView 5、TextInput 5、Modal 2、Text 1、ViewGroup 1），每条给「Recce 文件:行／RN 文件:行／影响／建议」；已修 4 条、待修 10 条，并给了修复顺序 ① 这套「逐文件对读 + 行号级证据 + 已修／待修状态表」是最可复用的工作方法，该固化成周期任务（每个 RN 大版本发布后跑一次）。② 最关键的自觉是作者主动标注的那条：maxLength 注明「RN main 同位置也是同样写法，不是相对 RN 的差异，但确实是崩溃点」——等于说 diff 只能识别「与对照物不同」，识别不了「两边都错」，必须配一路不看对照物的审查（边界用例、静态分析）。③ 待修里的 Modal 生命周期、ViewGroup clipping 焦点保护，与触摸新架构的接管清单一脉，应合成一条主线排期 与上游 diff 是查差异的利器，但盲区是「两边都错」；差异扫描要配一路不依赖对照物的审查，否则修完一轮剩下的全是共同错误
安全区域（1.33，排期跟随 1.30 小版本／主版本 1.32） iOS 已有 safeAreaDidChange 把安全区域值传给 recce-ui，Android 没有；核心问题是 Recce 内核无法判断当前页面是否沉浸式，所以返回的 safeArea-top 一直有高度 结论是「Recce 暂不改动，改容器侧」：短期由容器自己维护沉浸式状态并自己发事件；长期由容器在 url 里携带安全区域信息（是否沉浸式、top 和 bottom）。实现列了四个候选（setOnApplyWindowInsetsListener 挂 RecceRootView／挂 DecorView／重写 onApplyWindowInsets／在 onGlobalLayout 里追加检查），逐个标了「首次加载／旋转／键盘弹出是否触发」 ① 这是 18 份里「边界划得最清醒」的一份：没在错误的层硬凑，而是把「内核不知道沉浸式」这个信息缺口写成结论。② 长期方案用 url 传参会把会变的状态做成一次性快照，更优是把沉浸式作为「可查询属性 + 变化事件」暴露，形式与 iOS 已有的 safeAreaDidChange 一致，顺手对齐双端语义。③ 候选取舍标准该从「触发时机全不全」扩到「每帧成本」，明确只在 insets 变化时计算 一个值算不对时，先问「这个信息在哪一层是已知的」，答案不在自己这层就明确划出去，不要在错误的层叠补丁；一次性信息走 url，会变的状态走属性 + 事件

四、该改的六件事

# 改什么 为什么 怎么做
1 把「资源从哪来」抽成一层 Lottie、SVG、bundle 内字体三份方案各自定义路径或前缀规则，是同一个抽象缺失被付了三次成本 定一个资源来源接口（bundle／data URI／远端／宿主 assets），新能力只注册来源，不再发明路径约定
2 给所有包体相关的方案建一份共享的体积清单 Yoga 的体积在两个文档里出现 428KB 与 489.52KB 两个口径，本身就是「没有唯一出处」的证据 清单写清测法（构建类型、abi、压缩前后），方案里只引用不重算
3 把「上游当对照组」写进验收标准 背景重构已经做到了（三端各一台 + RN 写同一份用例跑第四台），其余方案没有 凡是「对齐 RN／对齐上游」的方案，验收项里加一条同机对照
4 差异扫描改成周期任务，并配一路不看对照物的审查 逐文件对读只查得出「不同」，查不出「两边都错」（maxLength 那条已证明） 每个 RN 大版本发布后跑一轮 diff，再跑一遍纯边界用例与静态分析，两条独立结论合并才收口
5 重构类方案把「清债」写进立项收益 立项只写「支持 BoxShadow」「支持 hitSlop」时，这类方案在评审中很难拿到优先级，而三份重构的收益大头都在清债 立项页里把「顺带修掉的历史问题清单」与能力目标并列
6 交付前给数字配「对照物」 18 份里只有 5 份有可复核数字；多年后判断对错说不清，多半不是选错了，而是没留下可复核的对照 把「对照物是谁、在什么设备上、测几次」写进文档——这条不需要额外交付成本
